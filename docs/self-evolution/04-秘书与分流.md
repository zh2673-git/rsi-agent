# 秘书角色 + 复杂度分流：方案与落地

> 来源：用户 2026-11-09 指令——「deepseek-paper 应与 GitHub 仓库同步」「继续需要 router」
> 「除 router 外，本 agent 缺一个秘书角色，它应具备所有工作区的视角：我 @它，它能总结所有
> rsi-agent 的任务/灵感、哪些做了哪些没做、哪些可以交给谁（拥有什么技能的人）」。
> 工作模式：**正向 + 优化混合**（project-dev §4/§6）——新增一个角色，同时给既有提示词加一条分流规则。
> 落地路径：`runtime/` 写保护 → 核心改动走 `scripts/patches/s*.json`；角色本体是 `skills/secretary/`。

---

## 0. 为什么是「两个东西」而不是一个

用户的表述里其实是两个诉求，混在一起会互相拖累：

| 诉求 | 本质 | 归属 |
|---|---|---|
| 「我 @它，它帮我总结所有任务/灵感、哪些没做、能交给谁」 | **视野**问题：谁掌握全局状态，谁负责回答「现在什么情况」 | 秘书（角色 + 聚合工具） |
| 「继续需要 router」 | **成本**问题：一件事该用多重的手段去做 | 分流（提示词接缝） |

合在一起做会得出一个错误的实现：让「秘书」同时负责分流。但秘书的价值是**看得全**，
分流的价值是**算得省**——前者要读全部状态（贵），后者要在开工前用最少的信息做判断（便宜）。
把它们塞进同一段提示词，结果是每轮都付「读全部状态」的钱去换一个「二选一」的判断。

**所以：秘书是唯一有全局视野的角色（读）；分流是所有轮次共享的一条判断规则（省）。**

---

## 1. 本质与时空契约

**秘书的本质**：一个**有全局读写视野的协调者**，而不是另一个执行者。

它和生产线的分工是：

| 角色 | 视野 | 做的事 | 不做的事 |
|---|---|---|---|
| worker（本 agent 平时） | 当前工作区 + 当前任务 | 改代码、跑测试 | 不负责回答「我手上一共有几件事」 |
| router（本方案 §3） | 只看本轮这句话 | 判复杂度、定档位 | 不读看板、不查历史 |
| **秘书（本方案 §2）** | **全部工作区 + 全部任务/灵感 + 技能库** | 盘点、归因、派活、催办 | **不动手干活**（动手仍是 worker，且仍走项目流程） |

「秘书不动手」是刻意的边界：一个同时负责盘点与执行的角色，必然把盘点结果本身当成执行依据，
于是「总结」会退化成「边做边总结」，用户拿不到一份只读的快照。

**时空契约**：

| 契约 | 内容 |
|---|---|
| 空间归属 | 看板数据仍只有一本（`<RSI_HOME>/.rsi/board.json`，见 `board.py::data_root`）；秘书工具**只读**，**不写**看板——写通道仍唯一是 `board.py` 与 `/api/board`。 |
| 时间流 | 「现算不缓存」：每次 @秘书 现读现渲染。理由是看板分钟级变化，缓存只会让用户拿到上一秒的答案（与 `board_ctx.rs` 同一判据）。 |
| 规则拦截 | 输出有界（字符上限、条数上限）；只读快照，不改任何文件；越界（无工作区 / 坏 JSON）降级为「该项缺失」而不是整体失败。 |

**为什么秘书工具只读**：用户的诉求是「我 @它，它告诉我情况」。若秘书能写，则「告诉我没做」
会自然滑向「顺手帮我做掉」，用户失去「只问答」的入口。写仍由 worker 承担，且写之前要过 rsi-board 的四问。

## 2. 秘书：四层设计

### 2.1 数据规范（空间里放什么）

不新增存储。秘书读的是**已经存在的三份事实**：

| 事实 | 来源 | 为什么是它就够 |
|---|---|---|
| 任务做了没有 | `board.tasks[].status` + `progress` + `evaluation.verdict` + `outcomes` | 「做了没有」在数据上就是 status，加上「有证据」= verdict/checks，加上「做成了什么」= outcomes |
| 灵感归谁了 | `board.inspirations[].status` + `tasks[]` | 采纳关系本来就双向记录，无需第三份 |
| 谁能干什么 | `skills/*/skill.json`（name/description/outputs/tools） | 技能就是「部门」的物理形态；`resourcing.skills` 是既往派活的证据 |

**明确不造的东西**：不建「人员表」、不建「能力矩阵文件」。理由——能力矩阵一旦落盘就会
和技能目录不同步，而技能目录本来每次 `skills.list` 都重扫（assets 插件已是这个语义）。
从既有字段现算，与 `board_cluster.py` 的裁决同源（那里已明确写「不造第二套真相」）。

### 2.2 数据存储（空间落在哪）

```
<RSI_HOME>/.rsi/board.json          ← 任务与灵感（已有，唯一一本账）
skills/<name>/skill.json            ← 技能契约（已有）
```

秘书工具 `scripts/secretary.py` **只读**这两个位置。

### 2.3 数据流转（时间轴上怎么变）

```
用户 @秘书 / 说「现在什么情况」
   ↓
secretary.py brief            （一次进程，纯读，现算）
   ├─ 任务：按 status 分组 → 每件给 一行结论 + 是否可复现（verdict/checks）+ 下一动作
   ├─ 灵感：open 且未被任何任务采纳的 → 列表（这是「还没人认领的想法」）
   ├─ 派活：把 open 任务 / 未采纳灵感 按「所需技能」映射到「现有技能能覆盖吗」
   └─ 阻塞：blocked 状态 + 有 checks 但 verdict≠pass 的「自称已完成」
   ↓
一段有界的纯文本（≤ 上限字符），直接进上下文
```

关键设计：**「哪些能交给谁」是一个 join，不是一次推理**。
join 的两侧是「任务需要的技能」与「技能库实际有的能力」；推理只用于两侧都缺的情况（该造技能）。

### 2.4 数据接口（外部入口）

| 入口 | 形态 | 用途 |
|---|---|---|
| `python scripts/secretary.py brief [--json] [--limit N]` | CLI，stdout | 用户 @秘书 时 agent 调它一次 |
| `skills/secretary/SKILL.md` | 技能目录 | **怎么问、怎么答、答什么不答什么**（判据在这里，不在代码里） |

不做 HTTP 端点，理由：UI 左栏的看板本身就是这块数据的可视化形态，再加一个端点是与它竞争。

## 3. 分流（router）：一条判断规则，不是新模块

### 3.1 现状与真实缺口

已有（`skills.rs` / `board_ctx.rs`）：
- `user_wants_task_plan()`：判「本轮是不是交代一件成规模的事」→ 决定是否注入看板规范全文；
- `decompose_hint()`：要求 `plan[].owner = self|subagent|skill`；
- `parallel_hint()`：判「哪几步可以并行」。

缺的是**入口处的三档默认值**：现在只有「像任务」与「不像任务」两态，
没有「像任务，但小到不值得开全套流程」。实测后果（trace s-mw5uq7sz）：15 轮 chat 共 1922 次工具调用、
单轮最多 245 rounds——`Get-Content README.md` 这种活也走完「探索→计划→看板→验证」。

### 3.2 三档划分（判据必须可落地，否则会被忽略）

| 档 | 判据（任一命中即入档） | 纪律 | 不做什么 |
|---|---|---|---|
| **S 直接答** | 一次性问题 / 单命令 / 单文件小修 / 纯查询 / 长度很短且无动作词 | 直接答或一次工具调用；不建任务、不写 plan、不注入流程规范 | 不探索仓库、不开 todo、不建看板条目 |
| **M 小改** | 单个文件/模块内的确定改动，验收一句话说清 | 读→改→验（3 步内）；更新已有任务的 plan 步态，**不新建任务** | 不写 PLAN.md、不派子代理、不做架构审计 |
| **L 项目级** | 多模块 / 跨文件契约变更 / 新项目 / 架构解读 / 用户明确要方案 | 先 load `project-dev`，走模式判定 → 计划 → 实施 → P/Q/I 验证 | 直接开写（必须先有 PLAN 或 program.md） |

**判据为什么这样写**：不用「行数」或「token 数」这类模型无法可靠自估的量，而用
**可观测的对象数**（几个文件、几个模块、需不需要方案）——这些在动手前看目录就能数出来。

### 3.3 接缝位置

`skills.rs::skills_appendix` 里新增一段 `routing_hint()`（照 `decompose_hint` /
`parallel_hint` 的既有纪律：新增能力单独成段、独立可回退），挂在 `parallel_hint` 之后。
门控与既有段一致（`has_board_cli()`）。

**为什么不改 `user_wants_task_plan()`**：那个函数是布尔门控，改它会影响既有的 5 个调用点
与已锁定的回归测试；分流要的是「注入了之后怎么分级」，是注入内容的问题，不是门控的问题。

## 4. 验证（P/Q/I）

- **P 前置**：`scripts/board.py`、`skills/` 可写；`runtime/` 走补丁。
- **Q 后置**：
  - `secretary.py brief` 在真实板上跑出：任务分组数量与 `board.py stats` 一致（可机检）；
  - 反证：造一个「灵感已采纳但任务全取消」的板，秘书必须把它列为「无人认领」；
  - `routing_hint` 的三档判据有回归测试（在 `lib.rs` 的测试块里加一条，与
    `want_task_plan_detection` 并列）。
- **I 不变量**：
  - `pytest` 全绿（含 `test_skill_sync` / `test_board_contract`）；
  - `secretary.py` 不写任何文件（测试断言 mtime 不变）；
  - 既有提示词段一字不动（`decompose_hint` / `parallel_hint` 锚点不改）。

## 5. 已评估不做

| 方案 | 为什么不做 |
|---|---|
| 给秘书一个可写看板的工具 | 「盘点」与「执行」分开才有只读快照；写通道已唯一 |
| 能力矩阵落盘成 `capabilities.json` | 会与技能目录不同步；技能目录每次重扫已是权威 |
| 用 LLM 判断「谁能干」而不是 join | 派活是数据问题（`resourcing.skills` ∩ 技能库），交给推理只会得到自信的胡说 |
| 把 router 做成配置项 | 三档默认值应当是恒定纪律，不是用户要调的旋钮；可调只会让它被关掉 |
| 新建 HTTP `/api/secretary` | 与左栏看板竞争同一份数据的两种呈现，收益低 |
