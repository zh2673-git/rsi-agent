## 0. 五条灵感的原话与落点对照

| 灵感 | 原话（节选） | 本轮落点 | 不做什么（明确边界） |
|---|---|---|---|
| I-01 | 「agent 需要自行在计划中写清楚…**是否需要进一步的进行细分**…是否需要调用子代理…考虑好任务的复杂度」 | `plan[].owner`（self/subagent/skill）+ `parent` 子任务 + `decompose_hint` 提示词段 | 不做递归任务树（只一层 parent）、不做自动调度（owner 是**决策记录**，不是调度指令） |
| I-02 | 「任务看板和灵感看板没有可编辑的功能吗，比如可以删除掉。**回滚的时候自动保留之前的文字**…执行排队也可以支持编辑或者复制？」 | 灵感 `✎` 改 / `🗑` 删（CLI + UI 双侧）、队列行 `✎` 改 / `⧉` 复制、回滚草稿保留 | 任务由 agent 建与推进，UI 仍**不给** task 写 op（B 轮裁决不变），删除走 CLI |
| I-03 | 「任务看板可以组成一个**活的弹窗**…任务看板是一个标签…每个任务会呈现出有哪些人财物，而且可以显示具体的比如模型、技能、工具、进度以及具体的计划、实施方案」 | `▤ 看板` 按钮 + `#board-win` 弹窗：按 kind 分标签、任务卡默认全展开（人财物/计划/分解/验收/检查/产物/对话关联） | 不做自由拖拽排布、不做多窗口（C 轮「有约束」裁决不变） |
| I-04 | 「会话框是用户与 agent 交互的唯一地方…可以从中分析出用户的习惯，以及对应回答模型的特点与习惯…agent 需要有这种**留存上下文**的机制」 | `.rsi/profile.json` + `scripts/profile.py`（章节 + 观察）+ `profile_ctx.rs` 有界注入 + `profile.py brief` | 不存聊天原文（trace 已有全量且可回滚）；只固化**提炼出的规律** |
| I-05 | 「只有一个会话，但可能执行多个任务，所以是否应该在会话窗口对应任务在运行时追加对应地方的会话、也支持排队、编辑？还是说采用 @ 之类的形式？」 | **采用 @ 形式**并把它做成可回溯的：`user` trace 事件带 `refs` 字段 + `/api/board/link` + `board.py link` | 不做「每任务一个子会话窗口」（会推翻单会话形态与回滚语义） |

I-05 的判断依据（为什么选 @ 而不是分窗）：任务与对话的关系是**多对多**——一件任务会跨
很多轮，一轮里也会谈到多件任务。分窗把多对多压成一对多，必然要发明「切窗口」的规则；
而 `@T-...` 是用户本来就会写的东西，代价为零，且天然留下可反查的关联键。分窗唯一的好处
（视觉隔离）在本轮由「看板弹窗」补上了。

## 1. 本质与时空契约

**本质**：这五条其实是同一件事的五个面——**让「任务」这个对象在时间上可追溯、在空间上
可摊开、在决策上可核对**。

- I-02/I-03 解决「看得见、改得动」；
- I-04 解决「记得住」（跨会话的长期上下文）；
- I-05 解决「对得上」（这一轮谈的是哪件、这件在哪几轮谈过）；
- I-01 解决「说得清」（这件活被拆成几步、每步谁干）。

**时空契约**：

| 契约 | 内容 |
|---|---|
| 空间归属 | `.rsi/board.json` 独看板（任务/灵感/布局）；`.rsi/profile.json` 独画像；trace 归 memory 插件。三者不互相写。 |
| 时间流 | 看板写入=「四时刻」事件式（建/迁移/阻塞/完成）；画像写入=「结论凝固」式（稀疏）；注入=每轮现读现渲染，不缓存。 |
| 规则拦截 | 枚举封闭（owner/insp status/kind）、长度与条数上限、坏文件拒写、跨语言同源常量由测试锁死。 |

## 2. 数据契约增量（与 C 轮兼容，只加字段）

```jsonc
// task.plan[]  —— 新增 owner / note
{ "step": "...", "status": "pending|in_progress|completed|cancelled",
  "owner": "self|subagent|skill",        // 缺省 self
  "note": "可选" }

// task.parent —— 新增：本任务由哪个任务分解而来（"" = 顶层）
"parent": "T-20261108-02"

// trace user 事件 —— 新增 refs 字段（不新增事件类型）
{ "type": "user", "text": "...", "refs": ["T-...", "I-..."] }

// .rsi/profile.json —— 新文件
{ "version": 1, "updated_at": "...",
  "sections": [ {"id":"user-lang","kind":"user|model|workflow|env",
                 "title":"...","body":"≤1200","updated_at":"..."} ],
  "notes":    [ {"id":"N-YYYYMMDD-NN","kind":"...","text":"≤400","tags":["..."],"created_at":"..."} ] }
```

`owner` 缺省 `self` 是刻意的：**不写 ≠ 委派**。若缺省成 `subagent`，模型会靠「没填」
隐式放大工作量；缺省 `self` 则逼它显式声明「这一步我要交出去」。

## 3. 逐条设计

### 3.1 可编辑与删除（I-02）

| 层 | 改动 |
|---|---|
| CLI | `insp-edit`（--text/--tags，部分更新语义）、`insp-rm`（adopted 需 --force）、`task-rm`（子任务摘 parent、灵感引用清空、未完结给 warning） |
| HTTP | `POST /api/board` 增 `inspiration.edit`（至少给一项）、`inspiration.rm`（adopted 409 需 force） |
| 前端 | 侧栏灵感行 `✎`/`🗑`；弹窗灵感行同款；队列行 `✎` 就地改 / `⧉` 复制到输入框 |

**删除的引用完整性**是这一块的真正难点。删一个任务若连带删子任务，用户会丢进度；若留下
悬空 `parent`，前端会去找不存在的 ID。取舍：**摘链不连带**——子任务 `parent` 清空、
灵感 `tasks` 里指向它的引用移除，并在返回里明确列出 `detached`/`unlinked`。

**队列编辑为什么禁掉「执行中」那条**：那条的文本已经进了服务端 chat，改本地串不改服务端
事实——允许改会让用户以为改生效了。按钮直接禁用，而不是「点了没反应」。

**回滚草稿保留**：`rollbackTo()` 先 `stashDraftForRollback()`，`connect(0)` 之后
`restoreDraftAfterRollback()`。只在输入框**仍为空**时还回——用户回滚后已经打了新字，
覆盖他就是把刚打的字吞了。

### 3.2 看板弹窗（I-03）

**同源不同壳**：弹窗复用侧栏同一份 `layout.sections`（`boardSections()`）与同一批数据
（一次 `GET /api/board` 喂两处），不是第二套看板实现。差别只在呈现密度：

| | 侧栏 | 弹窗 |
|---|---|---|
| 任务 | 一行摘要（可展开） | 卡片**默认全展开**：人财物 / 计划(含 owner) / 分解 / 验收 / 检查 / 产物 / 来源灵感 / 上级 |
| 章节 | 全部竖排 | 按 kind 分标签（kind 顺序仍由 C 轮钉死） |
| 指标 | 小格 | 宽卡 + 按状态明细 |
| 灵感 | 可加/改/删/引用 | 同款操作 + 更多正文可见 |

「插件化」的边界没变：弹窗标签仍只由 `kind` 决定，能加什么还是那三个白名单。**多开窗**
被否掉：要处理 z-order 与跨窗状态同步，收益不抵成本。

打开状态存 localStorage（`ra.boardwin`），刷新页面还记得上次开着。

### 3.3 习惯留存（I-04）

三层分工是这一节的核心判断：

| 层 | 载体 | 谁写 | 生命周期 |
|---|---|---|---|
| 原始交互 | memory 事件 / trace | 系统 | 全量、可回滚、不删 |
| 提炼结论 | `.rsi/profile.json` | **agent 主动写**（`profile.py`） | 跨会话长期 |
| 当轮上下文 | `profile_ctx.rs` 注入 | 系统读 | 每轮重读，有界 |

所以它**不是**「再存一份聊天记录」——trace 已经是那份记录了。存的是**结论**：用户偏好
怎么被回答、哪个模型在哪类活上靠不住、本工作区的既有约定、踩过的坑。

- 章节 = 结论（`user|model|workflow|env`，顺序钉死，同 id 覆盖）；观察 = 素材
  （`notes`≤60 条，满则丢最旧——观察可丢，章节才是结论）。
- 注入有界：整块 ≤1800 字符、章节 ≤8、观察 ≤6 条、单条 ≤120 字。空画像**不注入空壳标题**
  （每轮一句「暂无画像」是纯噪声）。
- 提示词纪律写明「**只写能活过本次对话的结论**」，并明确禁止记密钥、禁止重复看板已有的东西。

### 3.4 任务 ↔ 对话（I-05）

`chat.rs` 写 `user` trace 事件时，把本轮 `@T-/@I-` 提取成 `refs` **字段**（空引用不写，
保持旧 trace 形状）。沿用 Q 轮 `cursor` 先例：加字段不改 `FROZEN_EVENT_TYPES`，前端
`render()` 无需改。

反查两条通道同口径：
- `GET /api/board/link?id=…`（弹窗里点 `⌕ 对话` 现查，不预加载）
- `python scripts/board.py link <ID>`（人/agent 用）

`user_index` 与前端回滚定位口径一致（第几条 user 事件，0 基），所以「第 3 轮」点回去
就是那一轮，不是「大概在这个会话里」。

**为什么不靠模型登记**：`@T-...` 是用户明文写的，天然是关联键；让模型额外登记一次，
它忘了就断链。trace 是系统写的，跑不掉。

### 3.5 分解与委派（I-01）

用户要的是「考虑好复杂度」，但**软提示的产物是自述**（"这个任务比较复杂，我会分解"），
无法核对。故把它变成 `plan[].owner` 字段，每步必须回答「谁干」，验收时能数出来：

| owner | 判据 |
|---|---|
| `self` | 需要本轮上下文才能做（改刚读过的函数、按上次输出继续） |
| `subagent` | 可自包含、**产物是结论而非改动**（大范围调研、多文件阅读后总结、多方案对比） |
| `skill` | 仓库里没有现成能力，要先造技能/工具（这是「物力自造」的入口） |

提示词里同时写明**什么时候别拆**：「若子件验收条件与父任务相同，拆了只是把进度条切成
两段」。这一句比「请合理拆分」有用——它给了一个可判定的反例。

## 6. 过程留档（四个坑，都是真撞了才总结出来的）

### 6.1 「patch 是 anchor 的子串」→ 幂等判据失效

`index.html` 去重补丁的 `patch` 恰好是 `anchor` 的子串（去掉重复块后剩下的正是原锚点的
前五行），于是 `if patch in src` 在**未应用**时就为真 → 打印「已应用过」并静默跳过。
处置：给 patch 顶部加一行注释（`<!-- D 轮修正：… -->`），既解释改了什么，又让 patch
不再被 anchor 包含。**教训：删除型/收缩型补丁必须有独占标记行**，这与 §6.5（Q 轮）
「空串补丁」是同一族问题。

### 6.2 锚点复制了「不该重复的东西」

给 `board_ctx.rs` 加 `decompose_hint` 时，锚点取的是 `has_board_cli()` 整段函数体，
patch 里又原样带了一份 → `cargo check` 报 `E0428: has_board_cli is defined multiple times`。
处置：锚点只取**不会重复的最小片段**（函数尾部三行），patch 末尾再接新函数。
**教训：锚点要像外科手术切口，不是整块取景。**

### 6.3 宿主 env 被子进程继承 → CLI 读到另一个工作区的 trace

端到端第 11 项失败：`board.py link` 返回 0 条，而 HTTP 返回 1 条。根因是 `board.py` 优先
读 `MEMORY_DATA_DIR`，而这个 env 由**宿主进程**注入并被 bash 子进程继承——于是 CLI 读的是
宿主自己的记忆目录，不是当前工作区的。处置：判定顺序改成「**工作区里真有 trace 目录** →
env → 仓库缺省」。理由写进代码注释：`board.py` 是「贴在工作区里的工具」，它该描述**这个
工作区**的记忆。

**教训：环境变量不是「更权威」，只是「更近」。多工作区形态下，工作区内的实据 > 进程 env。**

### 6.4 grep 检查把看板自己扫进去了

端到端里想用「删掉 marker 文件」制造一次失败，结果仍然 pass——因为 `grep` 检查的 scope
是工作区根，而**marker 字符串已经写进了 `.rsi/board.json`**（任务本身记着它）。处置：失败
用例改成指向不存在的产物路径（`file` 检查），并把这条写进注释。

**教训：看板与 trace 都在工作区里，任何「扫工作区」的检查都必须假定它会扫到自己。**
要判「某文件的内容」就把 scope 收到最窄的目录，别用工作区根。

追加一条（补丁基线治理）：本轮合法改写了 7 条旧补丁的区域 —— `B2`/`B3`/`C5-LAYOUT-OP`/
`C-CTX-MOD`/`C-CTX-CHAT`/`FE2`/`FE7-BOARD` 终态内容均由 D 轮承接，按 P5b/O 轮先例转
`retired/`；`tests/test_board_contract.py` 的补丁在位断言改为「活跃 ∪ retired 并集 +
退役留档单独断言」，避免「退役 = 功能消失」的误判。
