# 知识落层与多域上下文

> 承接 `I-20261107-06`（知识该放哪一层）与 `I-20261107-07`（上下文该按什么分域）。
> 两条灵感其实是同一个问题的两面：**一条知识/上下文该落在哪个容器里，才既不会丢、
> 又不会在错的场合生效**。

## 0. 两条原话与本文要回答的问题

`I-20261107-06`：

> rsi-agent 现在的逻辑是不是最开始的时候就是有一些内置的工具和内置的技能，最主要的就是
> 创建 skill 和项目开发 skill 以及优化 skill 的 skill？对于记忆加载这种，它是作为内置的
> 还是做到工具使用的优化里面去？然后具体的比如推送至 github 这种，是作为用户的习惯、
> memory 还是说作为用户通用偏好技能，与特定任务无关的处理方式好一些。

`I-20261107-07`：

> 从用户角度来说，用户自己也是有角色分类的，比如生活、工作也会承担不同的角色，这些上下文、
> 记忆是不是也应该分开的……然后再进行具体的上下文细分，比如按照任务分？具体怎么分法比较
> 科学。

要回答的三件事：
1. **落层判据**——同一条知识，凭什么放 A 层而不是 B 层？（§1-§2）
2. **三个具体案例的答案**——记忆加载 / 推送 github / 造 skill。（§3）
3. **上下文怎么分域**——按角色？按任务？按什么才科学？（§4）

## 1. 已有的七条通道（先把事实摸清）

判据不能凭空发明，得先看清现在**实际存在**的容器各自是什么性格。

| # | 通道 | 载体 | 谁写 | 何时进上下文 | 性格 |
|---|---|---|---|---|---|
| 1 | 内置工具 | `plugins/tools/tools/*.py` | 出厂 | 每轮 schema 常驻 | **动作**，无语义领域 |
| 2 | 技能 | `skills/<name>/SKILL.md` | 人/agent | 目录常驻，正文 `load_skill` 按需 | **怎么做一类事**，可带工具 |
| 3 | 画像 | `.rsi/profile.json` | agent（`profile.py`） | 有界注入，每轮 | **跨会话结论**（偏好/脾气/坑） |
| 4 | 看板 | `.rsi/board.json` | agent（`board.py`） | 有界摘要 + `@` 引用装载 | **在办什么**，有生命周期 |
| 5 | 账本 | `ledger/` | agent（`ledger.py`） | 默认不进，按需召回 ≤5 条 | **做过什么**，含成本与教训 |
| 6 | 文档 | `docs/`、`PLAN.md` | 人/agent | 只读，按需 | **为什么这么做**，可审计 |
| 7 | trace | `memory/data/traces/*.jsonl` | 系统 | 不进（UI 重放 + 回滚真相源） | **原文**，全量不可改 |

这七条已经覆盖了「动作 / 方法 / 结论 / 在办 / 做过 / 为什么 / 原文」七个面，
**没有第八个面需要新容器**。所以判据的作用不是「再挑一个地方」，而是**排除**：
让每类知识只有一个正确落点，避免同一事实在两处漂移。

## 2. 落层判据：四问决策

四个问题按顺序问，**先前面的胜**（问 1 命中就不必问 2）。
为什么是这个顺序：从「最不可替代」到「最可替代」——先排除只有一处能装下的，
再处理有多个候选的。反过来排会出现「这个看起来也像画像也像技能」的僵局。

### 问 1｜它决定**动作怎么发生**吗？

- 是 → **内置工具**。例：读文件、跑命令、搜索。
  判据强化：如果拿掉它，agent 就做不了某类**物理操作**（而不是做得不好）。
- 否 → 问 2。

### 问 2｜换一个项目/工作区它**还成立**吗？

- 不成立（只对本仓/本工作区）→ **文档**（`docs/`、`PLAN.md`、`SYSTEM.md`）。
  例：「这个补丁机制的锚点语义」「本仓库提交信息行文」。
- 成立 → 问 3。

### 问 3｜它是**一类活的做法**，还是**一个偏好/结论**？

- 一类活的做法（有步骤、有阶段、有验收）→ **技能**。
  例：从零做项目、逆向读仓库、评测技能、发 PR。
- 一个偏好/结论（无步骤，只有「应该怎样」）→ 问 4。

### 问 4｜它有**生命周期**吗（会开始、会结束、有进度）？

- 有 → **看板**（在办）或**账本**（已办）。
  在办 → 看板；办完且要留成本/教训 → 账本。
- 没有 → **画像**。
  例：「回答用中文」「这个模型长命令容易超时」「用户讨厌冗长解释」。

> **trace 不在决策树里**：它不是「往哪放」的选项，是所有交互的**自动产物**。
> 任何「要不要记下来」的问题都不该指向 trace——那是系统行为，不是决策。

### 判据的反面：同一事实放错层的具体后果

这是判据真正有用的地方。放错不是风格问题，是有唯一解的故障：

| 事实 | 错放在 | 会发生什么 |
|---|---|---|
| 「中文回答」 | 技能 `git-ops` | 只在用 git 技能时生效，写文档时忘了 → 偏好在场但没生效 |
| 「本仓提交用 `type(scope): 中文`」 | 画像（全局） | 换个项目还在用本仓行文 → 上下文串仓 |
| 「这次要改看板左栏」 | 画像 | 一次性任务混进常驻 prompt，每轮白付 token |
| 「先写验收再写正文」 | 账本 | 按需召回才看，下次做同类活时根本想不起来 |
| 「bash 在 Windows 只能单行」 | 看板 | 任务完结后随归档消失，下次重踩 |

## 3. 三个具体案例的答案（I-06 的原话逐条作答）

### 3.1 「记忆加载是内置的，还是做到工具使用的优化里去？」

**答案：内置，且必须内置。**

判据路径：问 1「它决定动作怎么发生吗」→ 它决定的是**每一轮动作的前提**。
如果把记忆加载做成「工具使用的优化」（即让模型自己判断该不该 `memory.recall`），
代价是每轮一次工具往返 + 一次判断，而判断本身可能错（该召回却没召回 → 断片）。

现状已经是对的，且分了层（`docs/05-评测与记忆四层设计.md` §2.6）：

| 层 | 谁负责 | 是否每轮 |
|---|---|---|
| 工作记忆 | `memory.session` | 是（在 messages 里） |
| 结论层 | `profile_ctx.rs` **系统读** | 是（有界注入） |
| 情景/语义 | `memory-recall` 技能 + `ledger.py` | 按需（≤5 条） |

**唯一该由模型自己决定的是「要不要取第 3 层」**——因为那一层成本高（读文件），
且只有它知道当前任务是否需要历史。前两层属于输入，不该花往返去取。

### 3.2 「推送至github这种，是用户习惯 / memory，还是通用偏好技能？」

**答案：技能（`git-ops`）为主，画像只放一句指针。**

这两者不是二选一，而是**分工**：

- 「怎么提交、怎么推、什么行文、什么禁止」→ 有步骤、有铁律、有边界 → **技能**（已存在）。
- 「用户偏好提交前先看 diff」这类**跨任务的态度**→ 画像，但**只放一句**指向技能，
  不重复技能正文。理由：同一事实两处写，改一处忘一处时两边打架（见 §4 冲突规则）。

反例（要避免的形态）：「用户通用偏好技能」这个概念本身是危险抽象——它会把
「与特定任务无关的处理方式」堆成一个巨型技能，最后变成一个永远不被 `load_skill`
的垃圾桶。**没有触发场景的知识不该做成技能**（技能的价值一半在触发条件）。

### 3.3 内置技能是哪几个？`创建skill` / 项目开发 / 优化各自的定位

现状（`skills/` 12 个，`origin: preset` 6 个）：`creat-skill`、`project-dev`、
`repo-explorer`、`rsi-steward`、`skill-eval`、`tdd`——正是「造技能 / 做项目 / 读项目 /
编排 / 评测 / 验证」这六件事，即**自我迭代的元循环**。其余 6 个是 `origin: user`
（`git-ops`、`deepseek-paper`、`memory-recall`、`rsi-board`、`trace-analysis`、
`make-video`）。

这个分布是对的：出厂只装元循环，领域能力靠自扩展长出来。**判据上的一致性**：
元循环技能是「任何工作区都成立的一类活的做法」→ 问 3 命中 → 技能；
且它是造其它技能的技能，不能依赖自扩展先长出来 → 必须出厂。

## 4. 上下文分域：为什么不能按角色分

`I-20261107-07` 提出的直觉是「工作/生活」分域。**这个直觉的一半是对的**
（上下文确实该分），但分法要换。

### 4.1 按角色分的三个问题

1. **跨域同一事实要写两遍**。「回答简洁」在工作域和生活域都成立，写两处 → 必漂移
   （改一处忘一处，模型看到两个版本时不知道听谁）。
2. **角色边界本就模糊**。工作的技术决策影响个人装机（本仓就是例子：`make-video`
   是个人项目、`git-ops` 是本仓工作，两者共用一套 bash 单行约束）。按角色分域时，
   这条约束属于哪个域？
3. **误判成本不对称**。「该注入的没注入」只是少一点帮助；「错域偏好被自信注入」
   是**污染判断**——它比没有画像更坏，因为模型会基于错误的偏好做出看似合理的选择。

### 4.2 正确的判据：按**作用范围**分，只分两级

| 层 | 键 | 何时注入 | 判据 |
|---|---|---|---|
| 全局 | 顶层 `sections`/`notes` | 每轮都在 | 在任何域里都**成立** |
| 域 | `domains.<name>` 同形结构 | 当前域命中时 | 换到别的域就**错**（不只是无关） |

关键区分词：**「错」而不是「无关」**。

- 「回答用中文」换到哪个域都对 → 全局。
- 「提交信息用 `type(scope): 中文`」换到别的仓库就**错** → 域。
- 「偏好表格而不是长段」换到哪个域都对 → 全局。
- 「这个项目要在 Linux CI 上跑」在个人装机域就错 → 域。

### 4.3 为什么不做自动推断

**系统绝不替用户猜「这轮是工作还是生活」。** 理由就是 4.1 第 3 条：
猜错比不猜更坏。所以切域只能是**用户的显式动作**：

- `python scripts/profile.py use work` —— 写 `current_domain`（粘性，跨轮有效）
- `RSI_PROFILE_DOMAIN=work` —— 环境变量临时钉住（优先于文件状态，适合脚本/子代理）
- `use none` —— 回全局

系统侧（`profile_ctx.rs::active_domain`）只读这两个来源，**不产生**判断。

### 4.4 按任务分？不行

原话里还有「再按任务分」的可能。**明确否掉**：

- 任务是有生命周期的，域是稳定的。把任务当域 → 域数量爆炸（每个任务一个域），
  等于把画像退化成 trace。
- 任务的上下文归**看板 + 账本**：看板有 `plan`/`resourcing`/`acceptance`，
  账本有 `steps`/`cost`/`lessons`。它们天然按任务分段，且不常驻 prompt。
- 域的正确定位是「**少数几个稳定的作用域**」（上限 8），不是「每个任务一个」。
  超了就该用看板，不该用画像。

### 4.5 继承与冲突规则

- **继承**：域内未写的键回落全局。只写差异，不重复。
- **冲突**：域写同 `id` 即覆盖全局，注入时显式标注 `(overrides global)`。
  不静默覆盖——静默会让模型看到两个版本却不知道哪个生效。
- **不复制**：域块不复制全局内容。复制会让同一事实在 prompt 里出现两遍，
  模型改一处忘一处时两边打架。
- **ID 全文件唯一**：`note-rm <id>` 的 `--domain` 有三条隐式来源（参数/环境/粘性），
  两层若能用同一个 id，同一条命令在不同域状态下会删掉不同东西。所以 note ID
  跨层唯一（`all_note_ids` 汇总后再分配）。

### 4.6 v1 兼容

旧 `profile.json`（无 `domains`/`current_domain`）**照读为纯全局**：不迁移、不重写、
不丢条目。读侧把脏域键（大写/非法形状）折成合法值或忽略，写侧严格拒绝非法域名
（`use Work` 报错而不是静默变成 `work`——静默折叠会让用户以为切到了新域）。

## 5. 自扩展途径与三条通道的边界（防重复）

自扩展只有三条合法途径（与 `SYSTEM.md` 同源，因为这是**硬边界**不是建议）：

| 想加什么 | 唯一途径 |
|---|---|
| 知识/流程类技能 | `skills/<name>/SKILL.md`（目录名 = frontmatter `name`；需 `origin: user`） |
| 技能配套工具 | 技能目录内 `tools.json`（ToolSpec + `exec.cmd`）+ 执行器程序 |
| 外部服务工具 | 用户在 `config.json` `mcp_servers` / 设置面板配置 |

「新建技能」这条路本身就说明了 §2 判据的落点：**技能是唯一可自扩展的语义容器**。
画像有 CLI 且可自写，但它的形态被锁死（4 类章节 + 域名封闭）——它只能装结论，
不能装方法。这正是不把方法写进画像的结构性保证。

| 想记的东西 | 落点 | 不要放 |
|---|---|---|
| 任务进度/验收/产物 | 看板 | 画像（一次性，会污染常驻 prompt） |
| 一次工作的成本与教训 | 账本 | 看板（完结后归档，看板只留在办） |
| 一类活的做法 | 技能 | 画像（画像没有触发条件） |
| 本仓特有的坑 | 画像 `env` 章节 或 `SYSTEM.md` | 技能（换个项目就不该带着走） |
| 「该不该做」的决策史 | 文档 §已评估不做 | 画像（会长到没边） |
| 原文 | trace | 任何其它地方（不要复制原文） |

## 6. 验收（本模块）

- **P**：`profile v2` 文件可解析；v1 文件不被改动即可读；域名形状封闭。
- **Q**：域层写入/删除/切换/列举四类命令行为符合 §4.5；注入块全局段与域段各自有界；
  覆盖全局的同 id 在注入时可见 `(overrides global)`。
- **I**：既有 pytest 不回归；`cargo check` 零警告；v1 文件读后字节不变；无自动切域代码路径。

## 7. 未做与下一步候选

- **域的可视化**：现在只能用 CLI 看 `domains`，看板弹窗里没有域视图。
  要不要加需先回答「域是不是高频操作」——目前判断是低频（天级），不做。
- **域与看板任务的关联**：任务的 `resourcing` 里没有域字段，理论上可以
  「做这个任务时自动切到某域」。**故意不做**：这就是 §4.3 否掉的自动推断换个入口。
- **`resourcing.model` 真正影响调度**：仍只是决策记录（D 轮遗留）。
- **`owner: skill` 的现造闭环**：D 轮只做到「记录决策」，没做到「自动触发造技能」。
