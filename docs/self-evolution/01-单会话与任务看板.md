# 单会话 + 任务看板：把「人的思维模式」做进 UI 与运行时

> 用户构想（2026-11-07）：agent 应具备**人的思维模式**——从需求出发，先想清「怎么做」（方案/计划）、
> 「成立什么部门/角色」（技能）、「用什么模型（人力）最省」、「需要什么物力（工具）」，
> 并有「好坏标准」（评价体系）。
> UI 因此**不需要分会话层级**：面对用户的永远是一个会话框；项目分类由 agent 自己在工作区完成。
> 左侧看板 = **任务看板**（从会话总池里提炼，承载人财物分配与进度）+ **灵感看板**（碎片记录，可 @ 引入对话）。

## 0. 本质定义（先契约后代码）

| 问题 | 回答 |
|---|---|
| 本质 | 本迭代不是「加两个面板」，而是把**任务**提升为 agent 与用户之间的一等对象：会话是流，任务是账；流可以很长，账必须收敛。 |
| 空间归属 | 任务/灵感数据单写点 = `WORKSPACE_ROOT/.rsi/board.json`（`RSI_BOARD_PATH` 可覆盖）。**不进会话上下文**，按需检索；UI 经 `GET/POST /api/board` 读写，agent 经 `scripts/board.py` 读写，两侧同为「读-改-写 + 原子替换」，按 id 合并，避免互相覆盖。 |
| 时间流形态 | 任务生命周期 = 离散状态机 `planning → doing → verifying → done`（`blocked`/`cancelled` 为旁支）；不校验跳步（与 `todo` 工具同款由模型自律），但**状态枚举封闭**，写非法值即拒。会话本身仍是 ReAct 循环，本迭代不改。 |
| 规则拦截 | ① id 形状与唯一性；② 条数上限（tasks 200 / inspirations 500）；③ 字段长度上限；④ 状态枚举封闭；⑤ 路径必须落在 `WORKSPACE_ROOT` 内（Rust 侧常量路径，Python 侧 realpath 前缀校验）；⑥ 写盘 tmp+rename 原子替换，半截 JSON 不落地。 |

**为什么不做的事**：不新建会话树/任务引擎/DB；不改 `rollback` 语义；不引入前端框架；
任务看板**不允许自由拖拽排布**（用户明确「应该有约束，而不是随意排布」）——分组顺序由状态机固定。

## 1. 与「人的思维模式」的对应（人财物）

| 人的说法 | 系统落点 | 谁写 |
|---|---|---|
| 这件事怎么做（方案、计划） | `task.plan[]`：有序步骤 + 每步状态；`task.goal` 一句话目标 | agent（`creat-skill`/`project-dev` 前置思考的产物） |
| 成立什么部门、用什么角色 | `task.resourcing.skills[]`（技能 = 部门能力） | agent |
| 用什么模型（人力）效率最大化 | `task.resourcing.model`（`current` / 具体模型名 / `cheap`）+ `effort`（small/medium/large） | agent |
| 物力（工具） | `task.resourcing.tools[]` | agent |
| 好坏标准（评价体系） | `task.acceptance[]`（可核对的验收条目，非空才允许进 `verifying`） | agent + 用户确认 |
| 进度 | `task.progress = {done, total, note}` + `status` | agent（每步完成即更新） |
| 散碎的灵感 | `inspiration` 条目，状态 `open → adopted/archived` | 用户（UI 输入框）/ agent（提炼） |

**关键取舍**：任务由 **agent 建**、用户只读+可增灵感。理由：用户构想是「用户不需要管背后的项目分类，
agent 自己分类」——若让用户维护看板，等于把分类成本又推回用户。

## 2. 数据规范（board.json v1）

```jsonc
{
  "version": 1,
  "updated_at": "2026-11-07T12:00:00Z",
  "tasks": [{
    "id": "T-20261107-01",           // T-YYYYMMDD-NN，唯一
    "title": "≤120 字",
    "status": "planning|doing|verifying|done|blocked|cancelled",
    "priority": "P0|P1|P2|P3",       // 缺省 P2
    "goal": "≤500 字",
    "plan":   [{"step": "≤200 字", "status": "pending|in_progress|completed|cancelled"}],
    "resourcing": {
      "model": "current|cheap|strong|<模型名>",   // 人力
      "effort": "small|medium|large",
      "skills": ["creat-skill"],                   // 部门/角色
      "tools": ["bash", "write_file"],             // 物力
      "budget_secs": 0                             // 0 = 不限
    },
    "acceptance": ["可核对的验收条目"],             // 非空才允许 verifying
    "progress": {"done": 0, "total": 0, "note": "≤500 字"},
    "inspirations": ["I-20261107-01"],
    "artifacts": ["outputs/xxx.md"],
    "session": "main",                            // 提炼来源（单会话下恒为 main）
    "created_at": "...", "updated_at": "..."
  }],
  "inspirations": [{
    "id": "I-20261107-01",
    "text": "≤2000 字",
    "tags": ["≤32 字"],
    "status": "open|adopted|archived",
    "tasks": ["T-20261107-01"],      // 被哪些任务采纳
    "created_at": "...", "updated_at": "..."
  }]
}
```

上限：tasks ≤ 200、inspirations ≤ 500、`plan` ≤ 50、`acceptance` ≤ 30、`tags` ≤ 10。

## 3. 接缝与文件（四层设计）

### 3.1 数据接口（对外的口子）

| 面 | 契约 | 实现 |
|---|---|---|
| UI 读 | `GET /api/board` → `{ok, board, path}`（缺文件即建默认空板） | `host/src/web/api/board.rs::get_board` |
| UI 写 | `POST /api/board`：`{op:"inspiration.add", text, tags?}` / `{op:"inspiration.set", id, status}` / `{op:"refresh"}` | `board.rs::post_board` |
| agent 读 | `python scripts/board.py list [--compact]` / `show <ID>` / `stats` | `scripts/board.py` |
| agent 写 | `python scripts/board.py task-upsert --json <file|->` / `task-status <ID> <status> [--note]` / `task-progress <ID> <done>/<total> [--note]` / `insp-add "<text>" [--tags a,b]` / `insp-adopt <I-ID> <T-ID>` | 同上 |
| 提示词 | `skills_appendix` 追加「## Task board」段：建任务、人财物、验收、@引用解析 | `agent-loop/src/skills.rs`（补丁） |

**为什么 agent 走 CLI 不走技能工具**：技能工具的 `tools.json` 装载后默认**未启用**（需用户设置面板批准），
而 `bash` 是缺省启用集。让 agent 的写作通道依赖一个「要用户点一下才生效」的入口，等于把闭环断在配置上。
故 CLI 是**保证通道**，`skills/rsi-board/SKILL.md` 只承载「怎么想、怎么写」的知识，不声明 tools。

### 3.2 数据流转

```
用户一句话 ──► agent 判断是否值得建任务（creat-skill 前置思考）
                 │是
                 ▼
       board.py task-upsert（status=planning，写 plan/resourcing/acceptance）
                 │
                 ▼ 执行（ReAct 循环，工具/技能/子代理）
       board.py task-status doing → 每步 task-progress → verifying
                 │
                 ▼ 验收逐条核对 acceptance
       board.py task-status done（或 blocked 并写 note）
                 │
                 ▼
        UI：GET /api/board 轮询/手动刷新 → 左栏看板重绘（分组顺序固定）
用户灵感 ──► UI inspiration.add ──► .rsi/board.json ──► @I-xxx 在会话里被引用 → agent 读取并采纳
```

### 3.3 数据存储

单文件 JSON（`WORKSPACE_ROOT/.rsi/board.json`）。读写纪律：
读 → 解析（坏文件按空板 + `corrupt:true` 上报，不静默清零）→ 按 id 合并写入 → `board.json.tmp` → `os.replace`/`fs::rename`。
Rust 侧用 `std::fs::rename`，Python 侧用 `os.replace`，两者在 NTFS 上均为原子替换语义。

### 3.4 前端形态（约束布局，不是自由排布）

```
┌─ 侧栏（264px，固定分区，顺序不可变） ─┐
│ R rsi-agent        [实例徽章]         │
│ ── 任务看板 ────────  ⟳  ────────────│  ← 分区 1：按状态机分组，组序固定
│  ▸ 计划 2 · 进行 1 · 验收 0 · 完成 5  │     组内按 priority→updated_at 排
│  ▸ [T-…] 标题        P1  3/5          │
│ ── 灵感 ──────────  N 条 ────────────│  ← 分区 2：倒序，输入框在上
│  [＋ 记一条灵感…]                      │
│  ▸ [I-…] 文本…            open        │
│ ── 底部 ─────────────────────────────│  ← 分区 3：窗口/实例操作
│  ▣ 新窗口                              │
└───────────────────────────────────────┘
主区：单一会话（无会话列表、无「新建对话」）
```

### 5.4 保留 / 回退决策

- **全部保留**。无回退项。
- 已评估不做（防重复尝试）：
  - **SSE 加一路 `board` 事件流**：看板变化是分钟级，加事件类型会触发 `FROZEN_EVENT_TYPES` 冻结闸 + 前端 `render()` 改动，收益不抵成本 → 用 20s 可见性轮询。
  - **任务写走 UI 按钮**：违反「用户不需要管背后的项目分类」。UI 只留灵感入口。
  - **看板进每轮 prompt**：整块塞进去是 O(看板大小) 的每轮开销，且看板本就给人看 → 提示词只给「通道 + 什么时候写」，需要细节时 `show <ID>`。
  - **新建插件承载看板**：跨进程只为读一个 JSON；host 已是 UI 数据组合根。
  - **引入 chrono 做时间戳**：为 10 行日期换算加一个 crate 不值得 → 自带 `civil_from_unix`（Hinnant 算法，配 4 组已知日期单测）。

### 5.5 过程中踩到的两个坑（留档防复现）

1. **B4b 首版插入点拆散了既有 P2 补丁的锚点**（任务看板段插在「产物段之后」，而 P2 的锚点正是那段结尾）。
   `--dry-run` 立刻报 `[P2] FAIL 锚点未命中`。按 O 轮「退役 vs 改插入点」的先例选了后者：把看板段移到
   **自扩展段之后、产物段之前**，P2 终态与锚点同时保住。
2. **`write_file` 全量覆盖误伤了 19KB 的 block 文件**（想 edit 一段却写成了「只有那一段」）。
   用 `runtime/` 里已落地的同名文件 + `.bak` 比对后逐字节还原（`runtime==bak` 校验通过），
   再由补丁机制重新走一遍幂等——这也验证了「补丁终态 = 可复原的权威副本」这个设计价值。
