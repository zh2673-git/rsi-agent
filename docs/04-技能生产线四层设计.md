# 技能生产线四层设计

> 范围：从需求到技能生效的全流程。对应模块 A/B/E。目标是把 creat-skill 的方法论变成可执行、可校验、可回退的流水线。

## 1. 本质

在「轻资产技能」约束下，生产线是一个**带证据的状态机**：
每个技能都有契约（做什么/怎么算成功）、案例（怎么验证）、状态（能不能用）、历史（为什么变成现在这样）。

## 2. 数据规范

### 2.1 `skill.json`（技能契约）

```json
{
  "name": "demo-skill",
  "version": "0.1.0",
  "status": "draft",
  "description": "一句话说明做什么、何时触发",
  "triggers": ["用户说…", "遇到…"],
  "inputs": ["..."],
  "outputs": ["..."],
  "acceptance": [
    {"id": "a1", "criterion": "输出包含三个层级", "check": "assert"},
    {"id": "a2", "criterion": "难度可解释", "check": "rubric"}
  ],
  "requires": [],
  "handoff": ["artifact:docx"],
  "verification": "unverified",
  "source_level": "mixed",
  "created_at": "2026-10-31",
  "parent": null
}
```

字段约束：

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | 是 | kebab-case；等于目录名 |
| `version` | 是 | semver；晋升时递增 |
| `status` | 是 | `draft/candidate/active/retired` |
| `acceptance` | 是 | ≥1 条，且每条有 `check` 类型 |
| `verification` | 是 | `verified/partial/unverified` |
| `requires` | 否 | 依赖技能名；禁止环 |
| `parent` | 否 | 上一版本号或来源技能 |

### 2.2 `evals/cases.jsonl`

```jsonl
{"id":"c1","input":"把这段单元练习分成 A/B/C 三层","expect":"三层题目且每层有依据","rubric":"分层依据/覆盖度/可打印","weight":1,"signal":"judge","source":"用户真实需求","check":null}
{"id":"c2","input":"这个单元的词汇有哪些需要重点练","expect":"列出核心词汇并说明复现次数","rubric":"准确性/覆盖度","weight":1,"signal":"assert","source":"教材","check":{"kind":"contains","value":["复现次数"],"target":"output"}}
```

约束：

- 至少 3 条；candidate 起强制。
- 每条必须有 `id/input/expect/rubric/signal/source`；`signal=assert` 必须有 `check`。
- `check.kind` ∈ `contains / not_contains / regex / exact / any_of`；`target` 默认 `output`。
- `signal` 只能是 `assert/judge/human/test`。
- 来源必须可追溯（教材/用户/标准文档），不能写「模型认为」。

### 2.3 `evals/rubric.md`

```markdown
# 判分口径

| 维度 | 权重 | 通过标准 | 反例 |
|---|---|---|---|
| 分层依据 | 40% | 每层有可解释的难度依据 | 只按题号分组 |
| 覆盖度 | 30% | 覆盖本单元核心词汇/句型 | 漏掉重点 |
| 可用性 | 30% | 教师可直接打印 | 格式混乱 |
```

### 2.4 `state.json`

```json
{
  "name": "demo-skill",
  "status": "candidate",
  "active_version": "0.1.0",
  "versions": [
    {"version": "0.1.0", "score": 0.72, "signals": ["eval"], "at": "2026-10-31"}
  ],
  "last_promoted_at": null,
  "retire_reason": null
}
```

### 2.5 `registry/`

沿用 creat-skill 的两个文件，并加字段：

- `failure-fixes.md`：现象 → 根因 → 修正 → 复现案例 id。
- `exemplars.md`：标杆片段 → 为什么好 → 可复用结构。
- 每条必须有 `case_id`，否则无法回归。

## 3. 数据存储

```text
skills/{name}/
├── SKILL.md
├── skill.json
├── state.json
├── references/
├── evals/
│   ├── cases.jsonl
│   ├── rubric.md
│   └── results/{version}.json
├── registry/
│   ├── failure-fixes.md
│   └── exemplars.md
└── tools.json            # 可选，带工具技能
```

**版本与回退**：不做包管理；每次晋升前把 `SKILL.md + skill.json + evals/` 的快照写入 `ledger/evidence/{name}/{version}/`，回退时复制回去。复用现有文件快照能力。

## 4. 数据流转

### 4.1 十阶段状态机

| 阶段 | 输入 | 动作 | 输出 | 失败去向 |
|---|---|---|---|---|
| Intake | 用户需求 | 生成任务卡（目标 + 验收） | `task.json` | 反问用户 |
| Recall | 任务卡 | 查 active 技能 + 账本 | 候选列表 | 无候选则 Decide |
| Decide | 候选列表 | 值不值得造 | 决策 + 理由 | 直接 Execute |
| Author | 决策=造/改 | 还原专业 → 契约 → 写文件 → 写案例 | 技能目录 | 回退草稿 |
| Validate | 技能目录 | 静态校验 | 报告 | 修到通过或 Abort |
| Evaluate | 通过校验 | 跑案例 + 基线 | scorecard | Abort/回 candidate |
| Execute | 技能可用 | 执行任务 | 任务产物 | Verify 失败 |
| Verify | 产物 | 逐条核对验收 | 通过/失败 | Retro |
| Retro | 失败/修正 | 生成 failure-fix | registry 更新 | Promote |
| Promote | 证据 | 状态迁移 + 账本 | active/candidate | 保持原状态 |

### 4.2 Decide 门槛（必须写理由）

| 条件 | 结论 |
|---|---|
| 已有 active 技能可覆盖 ≥80% | 复用，不造 |
| 同类任务出现 ≥2 次且有稳定判据 | 造 |
| 一次性任务、无稳定判据 | 直接做，不造 |
| 只是信息不足 | 先取信息，不造技能 |
| 已有技能只差少量规则 | 改旧版，不新建 |

**禁止**：把「模型不会」当成「需要造技能」；先补信息或工具。

### 4.3 单点改动纪律

一次只改一层：

- 认知层（判断/规则）
- 执行层（工具/代码）
- 流程层（步骤/路由）

改多层会导致评测无法归因，必须拆成多轮。

## 5. 数据接口

| 接口 | 触发者 | 返回 |
|---|---|---|
| `load_skill("rsi-steward")` | agent-loop | 流程与路由 |
| `skill_validate(name)` | steward / install | 结构错误列表 |
| `run_evals(name, suite)` | steward | scorecard |
| `ledger_append(record)` | steward | work_id |
| `ledger_query(filter)` | steward | ≤5 条经验 |
| `skill_promote(name, evidence)` | 用户/规则 | 新状态 |

接口纪律：

- 返回结构化 JSON；错误必须有 `code/path/message`。
- 不把完整账本或完整技能塞进上下文；只返回摘要与路径。

## 6. 规则与晋升

### 6.1 证据分级

| 级别 | 证据 | 可用于晋升 |
|---|---|---|
| E1 | 用户明确确认/修正 | 是 |
| E2 | 确定性测试/eval 通过 | 是 |
| E3 | 真实任务结果（可观察） | 是 |
| E4 | 另一个模型盲评 | 仅辅助 |
| E5 | 同模型自评 | 否 |

### 6.2 晋升判据

必须同时满足：

1. `skill_validate` 通过；
2. `run_evals`：新问题修复，旧案例不退化；触发测试 ≥90%；
3. 至少一条 E1/E2/E3；
4. 知识层（SKILL.md/references/evals）满足 1-3 即自动晋升；改工具或核心层时，额外需要用户确认。

不满足 → 保持 `candidate`，但可用于「显式试用」，试用结果写账本。

### 6.3 回退判据

任一触发：

- active 技能在真实任务中连续 2 次失败；
- 触发误判导致明显错误；
- 评测发现旧案例退化。

动作：复制上一版快照回 `skills/{name}/`，状态回 `active`，账本记录原因。

## 7. 生命周期钩子

| 钩子 | 落点 | 动作 |
|---|---|---|
| `init` | 新建技能目录 | 生成 `skill.json` + `state.json`（draft） |
| `start` | 首次执行 | 记录 work_id，加载技能 |
| `stop` | 任务结束 | 写 verdict、成本、信号 |
| `destroy` | 退役 | 移出目录到 `skills/_retired/`，保留证据 |

## 8. 验收（本模块）

- **P**：`skills/` 可写；至少一个预置技能通过 validate。
- **Q**：故意缺验收段的技能被拒；候选低于基线不晋升；一次失败能生成带 `case_id` 的 failure-fix。
- **I**：技能目录格式不新增必需文件（除 skill.json/state.json/evals）；无包管理；无跨目录直写。
