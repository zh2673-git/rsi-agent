# 02 访谈协议

> 解决的问题：用户脑子里的行业知识是隐性的。要用问题把它逼出来，而不是让模型替他想。
> 本协议对应"问 AI 很多轮慢慢磨"的过程——把它变成有顺序、有追问、有停止条件的访谈。

## 一、顺序

**行业 → 流程 → 交接 → 验收 → 冲突 → 失败。**

先具体后抽象。先问"谁"，再问"交什么"，最后才问"怎么判断好坏"。一上来问"你的方法论是什么"，只会得到漂亮话。

## 二、五问与三层追问

### Q1 角色：这件事经过谁的手？

> "从开始到交付，中间经过几个人？他们各自最怕出什么错？"

追问：
- 为什么是他负责，不是别人？（逼出质量责任）
- 他不在的时候谁顶？顶的人会漏掉什么？（逼出不可替代性）

### Q2 工件：每个人交给下一个人什么？

> "上一个人交给下一个人的是什么？口头说，还是有个文件/表格？"

追问：
- 没有这个东西会怎样？（逼出翻译损耗）
- 下一个人拿到后第一件事做什么？（逼出工件的必含字段）

### Q3 验收：什么会被打回？

> "什么东西交上去会被打回？打回的时候对方会说什么？"

追问：
- 有没有"看着没问题但就是不行"的情况？那时候怎么判断？（逼出手感）
- 打回之后，最常改的是哪一处？（逼出高频缺陷）

### Q4 裁决：意见不一致听谁的？

> "两个人意见不一样时，最后听谁的？他凭什么？"

追问：
- 有没有吵到最后也没结论的？后来怎么处理？（逼出优先级）
- 这条规矩是写下来的，还是大家默认的？（区分制度与惯例）

### Q5 反例：最糟的一次什么样？

> "你见过最糟的一次是什么样？"

追问：
- 事后加了什么规矩防止再发生？（反例 → 规则）
- 这条规矩后来又被打破过吗？为什么？（规则的边界）

## 三、应对"说不清"

用户说"我也说不太清"是常态，不是障碍。四种破法：

| 情况 | 破法 |
|---|---|
| 太抽象 | 让他讲**最近发生的一件具体事**，从故事里抽结构 |
| 说"看情况" | 追问"看哪些情况"——这些就是决策树的分支 |
| 给不出标准 | 给二选一："A 和 B，哪个会被打回？" |
| 讲不出反例 | 换个问法："有没有哪次返工超过两遍？" |

**禁令**：不许替用户编答案。他不确定就记「假设」，进入试跑验证。

## 四、记录格式

每条都按这个格式记，方便后面直接填契约：

```
问题：<原话问法>
回答：<用户原话，不要润色>
抽出：<角色 / 工件 / 规则 / 裁决>
证据：案例 / 惯例 / 假设
```

## 五、停止条件

三条同时满足就停：

1. 五问都能给出至少一个具体案例；
2. 新回答开始重复已有内容；
3. 再问下去只能得到"差不多就这样"。

继续问不会更准，只会更烦。剩下的交给试跑。

## 六、访谈之后

- 填 `templates/profession-map.md`；
- 标出所有「假设」项，列成试跑清单；
- 假设超过三成，说明还没到能造技能的阶段，先补调研。
