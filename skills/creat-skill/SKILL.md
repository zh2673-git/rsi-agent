# creat-skill — 技能编译器

## 它产出什么

它**不直接干活**，它产出或改造**别的 skill**。一次成功调用的结果只有两种：

1. 一个新技能目录：`SKILL.md + references/ + templates/ + registry/`
2. 一份存量技能的诊断与改造（写进该技能的 `PLAN.md` 或 `registry/`）

合格标准一句话：**换一个人（或另一个 agent）只读这个技能，也能做出同等质量的结果**。封装规范见 references/07（自带最小兼容集），不依赖宿主是否内置 `skill-creator`；宿主另有要求时以宿主为准。

## 三句心智模型

1. **先还原，再编排**：不问"这件事该分几步"，先问"这行专业的人怎么分工、交接、验收"。方法论要从行业里长出来，不是拍脑袋拆出来。
2. **skill = 成熟生产体系 × AI 可执行化**：角色转成质量责任，工件转成交接契约，理论转成冲突裁决依据。
3. **还原有上限，试跑补下限**：理论只给方向，参数必须试出来；没有外部信号就标"未验证"。

## 何时不要用本技能

- 只是按规范建个空目录、套个 frontmatter → 直接读 references/07 做，不必走还原；
- 一次性任务、不会再重复 → 不值得造技能（技能是给**重复出现的判断**用的）；
- 用户已经给了完整流程，只要落盘 → 直接写，不必走还原；
- 只改措辞、触发描述或单个模板 → 直接走第 8 步 + 自检，不必跑全流程。

## 第 0 步 判定模式

| 用户意图 | 模式 | 入口 |
|---|---|---|
| "我要做一个 XX 技能" | 新建 | 第 1 步 |
| "看看我这个技能行不行 / 为什么不好用" | 逆向审计 | 第 8 步 |
| "优化 / 改造这个技能" | 优化 | 第 8 步 + references/06 闭环 |
| "把这次的做法沉淀下来" | 沉淀 | 第 8 步的沉淀分支 |
| 不明确 | 反问：从零造，还是改现有的 | — |

## 第 1 步 成熟度判定

| 类型 | 特征 | 还原路径 |
|---|---|---|
| **A 成熟行业** | 有分工、有交付物、有验收、有行规 | 角色谱系 + 工件链 + 校验标准（references/01） |
| **B 高手实践** | 有高手但没形成分工 | 高手决策序列 + 隐含判断（references/01） |
| **C 无先例** | 全新工作，没有前人 | 第一性原理 + 小样试跑（references/01） |

判不出来就按 B 走：先访谈，发现明确分工再升 A。**判定结果必须写进契约**，它决定后面工件的形态。

## 第 2 步 访谈五问

把"问 AI 很多轮磨出来"的过程变成有章法。每问必须落到**具体案例**，拿不到就标「假设」。话术与追问模板见 references/02。

1. 这行里，一件事从头到尾经过谁的手？
2. 每个人交给下一个人什么东西？
3. 什么东西交出去会被打回？
4. 两人意见不一致时谁拍板、凭什么？
5. 你见过最糟的一次是什么样？

**停止条件**：五问都有具体案例；新回答开始重复；再问只能得到"差不多就这样"。

## 第 3 步 转译三桥（行业 → AI）

详见 references/03。只记三条铁律：

| 桥 | 转成 | 铁律 |
|---|---|---|
| 角色 | 质量责任容器（不是职称） | 按**失败模式**合并，不按职称合并 |
| 工件 | 交接契约 | 必须可校验、可人工编辑、有明确消费方 |
| 理论 | 冲突裁决依据 | 理论推不出规则、规则变不成校验信号 → 删掉 |

## 第 4 步 收敛与裁剪

行业分工受人力、工时、资质约束，AI 不受；照搬一定过度工程。详见 references/04。

先定档位：**轻量档**（B 类，3–5 单元）/ **标准档**（A 类，角色 + 工件链）/ **深度档**（C 类，试跑驱动）。
预算：SKILL.md ≤ 150 行；单元超过 7 个必须合并；细节全部下沉 references。

## 第 5 步 试跑与验收

详见 references/05。三级验收，缺一级就标「未验证」：

1. **自检（可执行）**：写入 `evals/cases.jsonl`，每条含 `id/input/expect/rubric/signal/source`；assert 案例必须带可判定的 `check`（contained/regex/exact），跑 `python scripts/run_evals.py` 得到 scorecard；
2. **同行**：换个人只读技能，能不能做出同等结果；
3. **外部信号**：真实使用者 / 真实任务的结果（E1 用户确认 / E2 测试通过 / E3 真实结果）。

没有第三级时，把 `verification: unverified` 写进 `skill.json`，不许写成「已验证」。
自评（E5）只作提示，不能作为晋升依据。

## 第 6 步 落盘

标准结构（按需增删，不为对称凑文件；RSI 发行版另加 `skill.json` / `state.json` / `evals/`）：

```
<skill-name>/
  SKILL.md              # 只放：何时用/何时不用、模式、步骤、路由
  skill.json            # 契约：acceptance/verification/status（candidate 起强制）
  state.json            # 状态机：draft → candidate → active → retired
  evals/                # cases.jsonl + rubric.md + results/
  references/           # 理论与细节，一篇只回答一个问题
  templates/            # 可直接填的工件模板
  registry/             # 该技能自己的沉淀：exemplars / failure-fixes（每条带 case_id）
```

硬要求：

- 封装细节（frontmatter、description、目录、安装自检）见 references/07；description 必须写清「做什么 + 什么时候触发」；
- 落盘后必须过 `python scripts/skill_validate.py --skill <dir> --mode full`；结构不过不得进入 candidate；
- **Decide 门槛**：已有 active 技能覆盖 ≥80% → 改旧不新建；一次性任务且无稳定判据 → 不造技能；同类任务 ≥2 次且有判据 → 才造；
- 每个 reference 必须被 SKILL.md 引用，没被引用就删掉；
- 模板必须是能直接填的空表，不是说明文；
- 落盘位置默认与当前技能库同级（`skills/tool/<name>/`），用户指定则从其指定。

## 第 7 步 沉淀

每次交付后强制一次复盘，写两样东西：

- **失败-修正对**（最高价值）：现象 → 根因 → 改法 → 是否生效；
- **标杆卡**：适用条件 + 失效边界 + 为什么好 + 可借鉴的语法。

**匹配优先**：新建前先查 `registry/` 和已有技能，能改就不新建，差异大才新建。

## 第 8 步 审计存量技能（逆向模式）

六问，逐条给证据、不给结论：① 触发误/漏？② 本质说清了吗？③ 分解穷尽不重叠、算子对吗？④ 理论推得出规则吗？⑤ 工件可检查吗？⑥ 反例是真实的吗？

审计结论写进该技能的 `PLAN.md` 或 `registry/failure-fixes.md`；**不新增编号文档**，避免文档膨胀。已评估不做的方案记「已评估不做」，防止反复折腾。

优化模式必须走 references/06 的闭环：冻结基线 → 定问题 → 分层定位 → 单点改动 → 回归验收 → 保留/回退 → 记录。**没有基线就不叫优化，只叫改动。**

## 输出前自检（必须全过）

- [ ] 删掉所有理论段落，技能还能不能做出一致判断？不能 → 步骤在裸奔。
- [ ] 每个单元有没有一个"做错了长什么样"的信号？
- [ ] 有没有纯协调、不产出任何判断的单元？有 → 合并或删掉。
- [ ] 有没有理论推不出规则、规则变不成校验信号的？有 → 删掉那条理论。
- [ ] 换个人只读这个技能，能不能做出同等结果？
- [ ] 有没有把「未验证」写成「已验证」？
