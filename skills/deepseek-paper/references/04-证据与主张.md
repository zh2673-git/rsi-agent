# 04 从项目记录到研究主张：证据账本与研究点挖掘

> 用途：这是本技能**不同于通用写作**的一层。用户给的是「想法 + 项目记录」，论文要的是「主张 + 证据」。
> 铁法：**没有 artifact 的主张不许进正文**。宁可把成果写小，不许写没证据的句子。

## 4.1 输入是什么（先分级，别急着写）

| 输入类型 | 典型形态 | 能不能直接当证据 |
|---|---|---|
| 想法/动机 | 聊天记录、笔记、一句「我想做 X」 | ❌ 只能进 Introduction 的动机，且要标「我们的出发点」 |
| 计划 | 计划文档、PLAN.md、issue | ❌ 只能解释「为什么这么做」 |
| 实施 | commit、PR、代码、配置 | ⚠️ 只能支撑「我们设计了 X」，不支撑「X 更好」 |
| 测试/日志 | 测试报告、benchmark 输出、loss 曲线 CSV、trace | ✅ 主证据 |
| 迭代/对照 | 版本间对比、A/B、失败尝试记录 | ✅ 主证据（失败尝试也是资产，见 §4.4） |
| 外部基线 | 他人论文/榜单/API 实测 | ✅ 但必须写清口径（谁测的、怎么测） |

## 4.2 证据账本（写论文前必须先建）

字段与写法见 `templates/02-证据账本.json`。三条硬规则：

1. **每条证据必须有 `source`（文件路径 + 行号/commit/命令）**，没有 source 的一律标 `status: "todo"`，不许进正文。
2. **每条主张必须指到 ≥1 条证据 id**；指不到的主张降级为「设计选择」（`we design/we adopt`，不含量化断言）。
3. **数字必须可复算**：写进论文的每个数字，账本里要有原始数值 + 推导式（如 `4.2/3.1 = 1.35×`）。

`evidence_scan` 工具会自动扫项目目录，产出账本骨架（文件/行数/commit/测试报告/图表数据候选），并把缺 source 的项标 todo。**它的输出是素材清单，不是结论**——结论仍要人（或你）逐条判定。

## 4.3 研究点挖掘：五条挖掘线

从项目记录里主动找「可被写成贡献」的东西，按性价比排序：

| 线 | 问什么 | 挖到什么算研究点 | 进哪一章 |
|---|---|---|---|
| **异常线** | 哪个指标/现象和我们预期不一致？我们怎么解释的？ | 一个「反直觉但可复现」的观察（DeepSeek 的 aux-loss-free、MTP 都是这类） | 4.x/5.x Discussion，最强 |
| **取舍线** | 我们放弃了什么方案？为什么？代价多少？ | 一个「带代价的权衡」（如用 X 换 Y，量化代价） | 正文机制段 + 消融附录 |
| **复用线** | 哪个自研件被项目里多处复用/被迫重构？ | 一个「可被他人复用的机制」，能画成图 | Architecture/Approach 主节 |
| **失败线** | 哪些尝试无效？为什么无效？ | **`Unsuccessful Attempts` 节**（R1 有专节） | Discussion 章 |
| **成本线** | 我们比常规做法省了什么？省多少？ | 一张成本表 + 一句「同效果下省 X%」 | Infrastructures / 效率小节 |

挖掘纪律：
- **一条线最多出一个主研究点**；出三个以上说明还在堆料，没提炼。
- 研究点必须能写成「`<机制名>: <它带来的收益>`」的双段式小节名（V2 原文例：`Multi-Head Latent Attention: Boosting Inference Efficiency`）。写不出这个句式 → 还不是研究点。
- 若某条研究点在项目里**没有对照实验**，只能写成「我们观察到（we observe）」，或补一个最小消融。**补不出来就不写**。

## 4.4 失败尝试的写法（DeepSeek 的信用来源）

R1 §4.2 `Unsuccessful Attempts` 的三条结构，照抄结构不照抄内容：
```
<尝试名>: 我们试了 <做法>，期望 <预期>。然而 <实际结果>。
我们认为原因是 <机制解释>。<所以我们改用 <替代>。>
```
价值在于：读者会相信你没造假，并且别人能省下同样的弯路。**每条失败尝试都要给原因，不给原因的失败尝试是抱怨**。

## 4.5 主张强度分级（决定动词，见 03 §3.1）

| 证据强度 | 允许的表述 | 示例动词 |
|---|---|---|
| 多 seed / 多 benchmark 一致 | 强断言 | `consistently`、`pioneer`、`demonstrate` |
| 单次实验、单一 benchmark | 弱断言 + 限定 | `we observe that`、`shows competitive performance on <X> only` |
| 只有实现、无对照 | 设计陈述，禁止比较级 | `we design`、`we adopt`、`we employ` |
| 只有想法/计划 | 只能进 Motivation，且标为动机 | `we are motivated by`（不写成结果） |

**红线**：`outperforms` / `surpasses` / `significantly better` 三个词，每出现一次，账本里必须有对应 `compare` 证据（含基线与口径）。lint 会扫。

## 4.6 与既有 DeepSeek 论文的关系陈述（必写、易漏）

你的工作若与已发表工作相关，Introduction 里要用 `adopt` / `build on` / `differ from` 三档把关系说清，且**不得把自己的东西说成首创**：

- 沿用：`Following <Work>, we adopt <X> for <purpose>.`
- 扩展：`Building on <Work>, we extend <X> to <new setting>.`
- 区分：`Unlike <Work>, which <A>, our approach <B>, at the cost of <C>.`

第三档必须写代价（`at the cost of`），这是 DeepSeek 的诚实惯例；只写优势会被 rubric 判为「不像」。

## 4.7 验收（本文件对应的门禁）

- [ ] 账本里每条正文数字都能追到 source；
- [ ] 每章至少 1 条主证据，没有空章；
- [ ] 失败尝试 ≥1 条（M 类必须；T 类 ≥1 条可放 Discussion）；
- [ ] 与既有工作的关系用三档之一显式写出，且带代价；
- [ ] `outperforms` 类断言 100% 有 compare 证据。
