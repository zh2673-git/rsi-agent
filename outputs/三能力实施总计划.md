## 1. 顺序为什么必须是 RAG → 深度研究 → 教学

不是「先易后难」，是**数据依赖**：

```
RAG        产出「按内容取回片段」的能力
  ↓ 深度研究的账本要能被检索（否则下一轮 resume 只能靠 plan.json 的结论，
    细节全丢；有了索引才能「上次那个子问题我们查到什么」）
深度研究   产出「带出处的结论文档」（outputs/*.md）
  ↓ 课件 --from 指向的正是这份文档
教学       把结论变成可验收的教学材料
```

反过来做会各做一遍：先做教学，`--from` 只能指向零散文档；先做深度研究，它的账本
在下一轮不可检索，等于断点只恢复了一半。

## 2. RAG：已交付

### 2.1 做了什么

```bash
python scripts/index.py build                      # 建/更新（增量）
python scripts/index.py search "<问题>" --k 5      # bm25 排序，返回 path:line + 片段
python scripts/index.py stat                       # 索引体积/条目数
python scripts/index.py bench "<q1>" "<q2>" ...    # 与 grep 基线对比
```

**技术选型：FTS5 + CJK bigram，不是向量库。** 三条理由按硬度排：

1. **语料量级差三个数量级**。可检索单元（L2 摘要 56KB + `outputs/` 28 篇 + `docs/` 20 篇 +
   `skills/` 14 篇 + `patches/` 212 条）合计几 MB；向量库解决的是千万级文档。
2. **中文没有 CJK tokenizer，但 bigram 够**。索引侧把 CJK 连续串切成二元组
   （`内容检索` → `内容 容检 检索`），查询侧同样切，`bm25()` 给出的就是真正的相关性排序——
   这正是 `memory.recall`（子串扫描最近 2000 行、上限 5 条）缺的那一块。
3. **零新依赖**。`sqlite3` 是标准库，本机实测 3.41.2 且 FTS5 可用。

### 2.2 关键实现细节（踩过的坑）

| 细节 | 为什么 |
|---|---|
| 按 markdown 标题切块 | 命中后要能「打开那一节」，不是「打开那一段的中间」 |
| 原文落旁表 `chunk_text` | FTS 表里存的是 bigram token 串，**给人看不可读**；第一版直接展示它，输出是一堆「内容 容检 检索」 |
| 增量按 `(path, mtime_ns, size)` | 285 文件二次 build 全部 skipped，0.1s |
| 同一文件最多贡献 2 条结果 | 否则一个大文件占满 top-5 |
| 查询用 `OR` 而非默认 `AND` | 长查询任一词缺失会全灭；保召回、靠 bm25 排序 |
| `.rsi/index/fts.db` 是派生视图 | 可随时删掉重建，不入库（`.rsi/` 已在 .gitignore） |

### 2.3 P0 判据：先证明增量，再付出成本

方案 §3.5 定的判据是「如果 grep 已经能命中 18/20，就不要建索引」。本轮用 8 条真实风格的
「按内容找历史」查询做了对比（`index.py bench`）：

| 查询 | FTS5 命中文件 | grep 命中文件 | grep 够用？ |
|---|---|---|---|
| embedding 双通道怎么配置 | 3 | 6 | ✗（太多） |
| 补丁回灌到哪个版本 | 4 | **0** | ✗ |
| 回合暂停怎么做 | 4 | **0** | ✗ |
| env 污染导致测试红 | 5 | 15 | ✗（太多） |
| 深度研究账本设计 | 3 | **0** | ✗ |
| 教学能力落在哪层 | 5 | **0** | ✗ |
| FTS5 中文分词 | 4 | 2 | ✓ |
| 看板并行决策 | 3 | **0** | ✗ |

**grep 只在 1/8 上够用；FTS5 8/8 有命中且 top1 相关。** 差距的成因很清楚：
grep 是字面匹配，同义表述（「怎么配置」vs「配置示例」）一律漏；
而 bm25 在 bigram 上做的是真正的词频加权。

这个数字就是索引的价值证据——**它不是「我觉得有用」，是 7 条查询里 grep 给不出答案**。

### 2.4 接入方式

不是新造通道，是把 `memory_ctx::memory_ops_hint()` 那段（讲「L2 按天打开」）扩一段
（补丁 `E11-MEMORY-HINT-INDEX`）：

> 时间线回答「那天干了什么」；问「我们在哪决定的 Y」（按内容不按日期）时**不要 grep 整个树**
> ——中文表述会漏，命中也会太多。用 `index.py search`。精确标识符和代码仍用 `grep`/`symbols_search`。

### 2.5 没做 & 判据

| 没做 | 什么时候做 |
|---|---|
| `tools.json` 包装成模型工具 | 等它变成高频调用；现在 bash 直调足够（技能工具默认未启用，见方案 §1 通道 C 的闸） |
| 索引 trace 原文（74MB jsonl） | 不做。L2/L3 本来就是它的派生视图，索引原文等于绕过自己建的中间层 |
| 语义/向量检索 | 语料涨到十万级文档时再谈 |
| 定时自动 rebuild | 现在靠 `build` 增量 0.1s，手动足够；等出现「查不到但其实存在」再自动化 |

## 3. 深度研究：已交付

### 3.1 缺口是什么（不是缺搜索工具）

`web_search` / `web_read` / `task` 并行子代理本来就够跑「搜→读→综合」。缺的三件：

| 缺口 | 后果 |
|---|---|
| 撞预算墙后从哪继续 | `CHAT_BUDGET_SECS` 缺省 900s，到界即收尾；中间产物只在上下文里 → 全废 |
| 报告里的断言有没有出处 | 来源只以观测胸牌流向前端，跑完散在 trace，下一轮无法核对 |
| 读了哪些没用上 | 白花的 token，且掩盖「一段文字编到底」 |

### 3.2 做了什么

```bash
python scripts/research.py new "<主题>" --questions "q1" "q2" ...   # 立计划
python scripts/research.py --topic <t> add --url U --title T --quote "原文摘录"
python scripts/research.py --topic <t> done <idx> --note "一句话结论"
python scripts/research.py --topic <t> resume                      # 断点恢复
python scripts/research.py --topic <t> check <报告>.md             # 引用机检
```

三份产物在 `.rsi/research/<topic>/`：`plan.json`（断点唯一载体）、`sources.jsonl`
（append-only 账本）、`draft.md`（增量成稿）。

### 3.3 `check` 的三条判据（比「注意别瞎编」硬一个数量级）

| 判据 | 抓什么 | 实测 |
|---|---|---|
| 引用的 `[S*]` 在账本里存在 | 编造引用 | 报告引 `[S9]`、账本只有 S1/S2 → `missing:["S9"]` ✓ |
| 每条账本条目至少被引用一次 | 读了没用 | 账本 2 条、报告只用 1 条 → `unused:["S2"]` ✓ |
| 事实性段落无引用标记 | 无出处断言 | 200 字结论无 `[S*]` → `uncited_paragraphs` 命中 ✓ |

「事实性段落」判据：长度 ≥30 字的正文/列表项；标题、代码块、表格、引用块不计（它们不是断言）。
实测：一段无引用的正文 + 一条无引用的列表项 → 检出 2 段；表格行、代码块、标题均正确排除。

### 3.4 与并行子代理的协作纪律

`task` 子代理并行跑但**不写父账本**，只返回 `answer`。所以派活描述必须写死：

> 先 `python scripts/research.py --topic t add ...` 记账，再把结论写进 answer。

子代理有 `bash`，账本可达。这一条不改代码，但决定并行研究是「真并行」还是「并行然后丢细节」。

### 3.5 没做 & 判据

| 没做 | 理由 |
|---|---|
| 新增 `deep_research` capability | 不该进传输/生命周期协议层（方案 §1 通道 A 的反对理由） |
| DeepTutor 三段式流水线（research → outline → write） | 负收益：它的收益是「阶段间可人工介入」，而本仓形态是单会话连续对话，介入靠 `ask_user` 暂停已经够了 |
| 来源去重 / 可信度评分 | 等账本条目涨到几十条且出现重复来源再加 |

## 4. 教学：已交付（先做「产课件」，不做「当导师」）

### 4.1 甲乙之别（这是本节的核心判断）

| | 形态 | 受益者 | 适配度 |
|---|---|---|---|
| 甲：当导师 | 跨会话学习者模型、出题、判掌握、推下一步 | 一个人 | **低**——投入全新建 |
| 乙：产课件 | 把研究结论变成有结构可验收的材料 | 交付物 | **高**——输入输出都在已有通道 |

**先做乙。** 等真有人按课件学、并要求「按我的水平调整」，再谈甲——那时才有数据支撑
学习者模型该长什么样。现在做甲等于凭空设计一个没有用户的功能。

### 4.2 做了什么

```bash
python scripts/lesson.py <主题> init --from outputs/<源>.md
python scripts/lesson.py <主题> goal add "<目标>" --check "<检验问题>"
python scripts/lesson.py <主题> concept add "<概念>" --after "<前置>" --body "正文"
python scripts/lesson.py <主题> concept order      # 拓扑序；成环退出码 1
python scripts/lesson.py <主题> exercise add "<题干>" --answer "<答案>" --goal O1
python scripts/lesson.py <主题> build --out outputs/课件-<主题>.md
python scripts/lesson.py <主题> check             # 机检
```

### 4.3 为什么这算「课件」而不是「文档改标题」

四件事都可判，这才是区别：

| 件 | 不可判的反面 | 本工具怎么判 |
|---|---|---|
| 学习目标 | 「理解 X」 | 必须带 `--check` 检验问题；缺了 `check` 报 `E` |
| 概念顺序 | 作者想到的顺序 | Kahn 拓扑排序；成环报错**拒绝出稿** |
| 练习 | 泛泛思考题 | 必须 `--goal` 挂到目标 + 有 `--answer` |
| 验收 | 「我觉得写清楚了」 | `check` 退出码 |

### 4.4 实测

| 场景 | 结果 |
|---|---|
| 正常课件（2 目标 / 2 概念 / 2 练习） | 拓扑序 `[embedding, RAG]` 正确；`check` ok，退出码 0 |
| A↔B 互相前置 | `{ok:false, cyclic:[A,B]}`，退出码 1，build 拒绝出稿 |
| 目标无检验问题 + 练习未挂目标 + 无答案 | 三条 `errors` + 两条 `warnings` 全部检出 |

### 4.5 没做 & 判据

| 没做 | 什么时候做 |
|---|---|
| 甲：学习者模型 / 判掌握 / 推下一步 | 等课件真有读者、且提出「按我的水平调整」 |
| 自动出题（LLM 生成题干答案） | 现在人工写更准；自动出题需要判分器才能闭环，而判分器属于甲 |
| 图/动画等富媒体 | 已有 `make-video` 技能，需要时挂上去，不必内建 |
