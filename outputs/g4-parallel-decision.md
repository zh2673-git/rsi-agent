# G4 并行任务：技术判定（先想清楚，再动手）

## 已确认的既有事实

| 事实 | 位置 | 影响 |
|---|---|---|
| 同一轮的工具波次**已并行** | `chat.rs:632-635` `join_all(act_exec…)` | 「并行」不是从零做，缺的是跨任务 |
| 子代理已并行 | `act_exec` 在波次内被并发调用 | 一个回合内的多数委派已并行 |
| 同会话并发闸 K409 | `chat.rs:243` `gate.try_lock()` | **同一 session 第二路 chat 被拒** |
| 会话闸注释明确理由 | `chat.rs:201-203` | 互清取消标志 / 互踩 turn_starts 与流式 sid |
| 前端只有一个会话 | `app-core.js:12` `SESSION_ID="main"` | 用户看到「只有一个会话框」 |
| 流式旁路按 sid 对位 | `app-stream.js` `streamSid` | 一条 feed 只能呈现一路流 |
| 看板无跨进程锁 | `board.py` 读改写 / `board.rs` 同 | 两路并行写看板会丢更新 |

## 三条候选路线

### A. 前端多会话（每个任务一条 session）
用户能开多个任务并行，各自独立 feed。
- 代价：`index.html` 会话框结构重做、`app-events.js` connect/SSE 按 sid 多路、`app-stream.js`
  流式状态表化、`q-session.js` 队列按 sid（已 per-session，但 UI 未暴露）、历史恢复。
- 规模：前端 4 文件大改 + Rust 基本不动。**这是「再造一个 UI」，不是小改。**
- 风险：用户明说「不需要问我」，但这类大改若做歪，比不做更糟（回到「单调又混乱」）。

### B. 只做「agent 自行并行」——不动 UI
agent 在**一个回合内**用 `task` 子代理并行推进互不干涉的子任务，结果汇总成一条回答。
- 现状：**已经具备**（波次 join_all + subagent 已并行）。
- 缺的只有一件事：**没有告诉 agent 什么时候该并行、什么时候必须串行**。纯提示词问题。
- 代价：一处提示词 + 一条判据。规模极小，风险极低，且**完全符合用户原话**
  「agent 最好能自行判断……用户只需要知道结果就好了」。

### C. 跨回合并行（同一会话内，两件任务同时推进）
需要拆 K409 闸或给每个任务开 sid。
- 拆闸代价：取消标志/cancel 按 session 存 → 两路互相 cancel；`turn_starts`/`sid_seq`
  互踩；流式 sid 只有一份；回滚定位按 user_index 全局 → 一路回滚会串。
  **这不是「加个锁」能解决的，是要重构会话级瞬态状态表。**
- 若给每任务开 sid：前端要能选中「看哪一路」，等于回到 A。

## 判定

**做 B，并把 C 的真实边界写清楚。**

理由不是「B 便宜」，而是三条需求原文的对齐度：
- 用户要的是「**agent 自行判断**可以并行就并行，用户只需知道结果」——B 正好是这个形状。
- 用户没说「给我多个会话框」；他自己诊断出「目前只有一个会话框」，是在**提问机制**，
  而不是下需求「再造 UI」。
- C 需要重构会话级瞬态（取消/游标/turn_starts/流式 sid/回滚定位），一旦做错，
  症状是「点停止停错任务」「回滚删错对话」——比不并行危险得多。

**但 B 有一个必须先补的洞**：两件任务若都写看板，`board.py` 与 `/api/board` 都是
读→改→写且无跨进程锁，会丢更新（后写者用旧快照覆盖前者的新条目）。并行之前必须先修锁，
否则「并行」直接制造数据丢失。这一条**先做**，是本轮唯一的正确性前置。

## 落地清单

1. **G4a 看板写锁**（正确性前置）：`board.py` 与 `board.rs` 写盘前取同一把文件锁；
   锁不可得 → 明确 409/重试，绝不静默覆盖。
2. **G4b 并行判据进提示词**：告诉 agent 什么算「互不干涉」（不同文件、不同验证手段）、
   什么必须串行（同一文件、同一 build 目录、有先后依赖），以及「拿不准就串行」。
3. **G4c 并行结果汇总**：子代理并行后由主回合统一汇总成一条回答（已有 subagent 机制承载）。
4. **不再做**：前端多会话框、拆 K409 闸——写出理由留给后续轮次决策。
