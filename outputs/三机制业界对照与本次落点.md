# 三个机制在业界怎么做的，以及这次我们抄到了哪一步

> 配套任务 `T-20261111-05`（三步路线实装）。本文回答三个问题：这三件事**业界现状**是什么、**真正难的地方**在哪、**这次我们做到了哪一步**。
> 目的不是罗列（罗列没有增量），而是把「为什么选这个形态、放弃了什么」讲清。

---

## 一、工具 schema 按需装载（deferred tools）

### 业界现状

这个问题的学名叫 **tool overload / tool-space bloat**。三条主流解法，按侵入性排序：

| 解法 | 代表 | 判据 |
|---|---|---|
| **元工具**（meta-tool）：只给模型一个 `tool_search`，让它检索工具 | Anthropic 的 Tool Search、OpenAI 的 `tool_search` 实验特性 | 工具数 >> 单轮用量（几十到几百） |
| **按需声明**（deferred declaration）：schema 不预发，模型报名字才发 | Claude Code 的 ToolSearch、AutoGen 的 `FunctionTool.suggested` | 中等规模（十几件），名字可猜 |
| **检索式注入**（RAG over tools）：按当前 query 检索最相关的工具 schema | ToolRerank、Gorilla 系工作 | 极大规模 + 有高质量检索语料 |

三者不是互斥的。**共同结论是「全量预发一定亏」**：Anthropic 的工程博客给的数量级是——MCP server 接满后工具定义能吃掉 5 万 token，而单轮真正调用的工具中位数是 1-2 件。

### 真正难的地方

不是「怎么藏」，而是**藏了以后模型怎么知道它存在**。三条已经在生产环境暴露过的坑：

1. **藏太干净 = 功能消失**。模型不知道自己有 `pdf_extract`，就永远不会去用，转而用 bash + python 硬啃。所以必须留「名字 + 一句话」的摘要，且摘要要指向报名工具。
2. **报名后要真的能调**。很多实现只在「下发清单」层面做了过滤，忘了 `call` 路径也做了白名单校验，于是报过名的工具仍然调不通。
3. **不能惩罚直觉**。模型有时候会凭记忆直接调一个没报名的工具（尤其在被追问时）。如果这条路被封，它就得先花一次往返报名——这比省下来的 token 更贵。

### 这次做到哪一步

- **形态**：选的是「按需声明」（第二条），因为本仓库的规模就是十几到几十件（MCP server 数 × 每台工具数），不需要检索层。
- **摘要**：`deferred_line()` 只输出名字，上限 60 个（超出报 `(+N more)`）——一行摘要涨成三十行就又变成税。
- **报名**：保留工具 `load_tools({"names":[...]})`，结果**只回名字不回 schema**（schema 下一轮随清单下发，回喂一遍等于同一条信息花两遍 token；且 tool_result 另有 8000 字符上限，大 schema 会被腰斩成残缺 JSON）。
- **第 2 条坑**：`act_exec` 不检查 deferred 标记，`tools.call` 直通。端到端用例 `deferred_call_still_works_without_loading` 专门锁这条。
- **默认范围**：**只对 MCP 工具开**。技能工具通常 1-3 件且刚 `load_skill` 就期待可见，藏起来会让「装了却看不见」这个老坑复活（本仓库 D 轮踩过）。
- **没做**：不做检索式注入。理由：需要语料与评测，而当前规模下收益无法证明——**先能测量再优化**。

## 二、长会话记忆的分层

### 业界现状

「把历史压成摘要」是最老的思路，但分层（**L1 原文 / L2 摘要 / L3 结论**）是最近两年才收敛的形态。三个独立来源给出几乎相同的分层：

| 系统 | 分层 |
|---|---|
| MemGPT / Letta | recall storage（原文）/ archival storage（摘要）/ core memory（结论） |
| Claude Code | 会话 JSONL（原文）/ `/compact` 摘要 / CLAUDE.md（结论） |
| DeepTutor | `trace/*.jsonl` / `L2/<surface>.md` / `L3/<recent\|profile\|scope\|preferences>.md` |

**共同点比差异更有信息量**：三层是**必需的**，不是可选的优化。
两层的系统会在「上周那件事」这类问题上必然失败——读原文塞不进上下文，读结论记不住经过。

### 真正难的地方

1. **幂等**。摘要必须能重算且逐字节相同。否则用户无法分辨「记忆变了」与「摘要算法变了」——这是可信度的地基。
2. **召回不读正文**。声称「只读时间戳」很容易，实现里随手 `open()` 一天就破了。必须有一个**可核对的量**（我们用的是 `bytes_read == index.stat().st_size`）。
3. **日期算术**。让模型拿当前日期去减 `20261103` 是它最容易错的算术之一。`days_ago` 必须服务端算好。
4. **分天边界**。长会话会跨午夜。不切开的话「那天干了什么」会把两天的活算给一天。
5. **有界**。摘要层没有上限就只是把 trace 换个格式存一遍。

### 这次做到哪一步

- **三层齐了**：L1 = `memory/traces/*.jsonl`（原有）；L2 = `.rsi/memory/L2/<YYYYMMDD>.md`（新增）；L3 = `L3/index.json`（新增）；结论层 = `.rsi/profile.json`（原有，**并列不合并**——一个是经过，一个是结论）。
- **第 1 条**：`render_day(parse_day(x))` 逐字节幂等，`build` 每跑一次都**当场自验**（`verify_idempotent`），测试再锁一遍。时间只进 `index.generated_at`（元数据），正文不写当前时间。
- **第 2 条**：`recall` 的 `bytes_read` 恒等于 index 大小，测试断言这条。
- **第 3 条**：`days_ago` 在 Python 侧与 Rust 侧各实现一次（`memory_ctx.rs` 自带 `civil_days`，Howard Hinnant 算法，不引 chrono），两侧用同一 UTC 分天约定。
- **第 4 条**：按 `day_of(ts)` 分桶，跨天会话自然切成两条摘要。
- **第 5 条**：单天 ≤12KB、会话 ≤12、提问 ≤6 条、文件 ≤20；截断**显式标注**（静默截断会把「就这么多活」变成假事实）。
- **注入**：`memory_ctx.rs` 把「最近 7 天有哪些活、各多大」注入系统提示词（≤900 字符），要细节让模型按天打开 L2。
- **没做**：不做语义检索（embeddings）。理由同上——当前规模下「按天索引 + 模型自己挑」够用。

## 三、回合持久化与中途暂停

### 业界现状

「一次请求 = 一个可寻址、可恢复的对象」有两条成熟路线：

| 路线 | 代表 | 契约 |
|---|---|---|
| **事件溯源**（event sourcing）：turn 是事件流的一个区间，带游标（seq），客户端按 seq 补播 | DeepTutor 的 `turn_protocol` v2（14 种事件 + `seq` + `TurnQueryState.recovering`）、LangGraph 的 checkpointer | 事件是真相，turn 只是索引 |
| **快照恢复**（snapshot）：turn 存完整状态，恢复=载入快照 | OpenAI Assistants 的 `run` + `thread`、Temporal 的 workflow state | 状态是真相，事件是日志 |

**分歧点在「谁是真相」**。事件溯源的好处是**不可能不一致**（补播和实时读同一条流）；坏处是客户端必须自己重放。快照的好处是恢复一步到位；坏处是状态与日志可能分叉。

「中途暂停」这一层，两条路线都靠**把「等用户输入」建模成一个一等状态**，而不是「结束这一轮再开一轮」：

- LangGraph：`interrupt()` 暂停图执行，`Command(resume=...)` 恢复，**状态在图里不动**；
- DeepTutor：`ToolResult.pause_for_user` + `wait_for_input` 命令，回合不结束；
- OpenAI Assistants：`requires_action` 状态 + `submit_tool_outputs`，按 `tool_call_id` 接回。

**共同点**：恢复时必须按 `tool_call_id` 把答案接回**那一条调用**，否则模型看到孤立 tool 消息，严格协议下直接报错。

### 真正难的地方

1. **不复制事件**。turn 若自己也存一份事件，回滚截断 trace 时副本就成了幽灵。
2. **seq 的口径**。是每回合从 0，还是 trace 绝对下标？选每回合从 0 就要在两端各做一次换算——换算层是「客户端和服务端各算一次」这类 bug 的产地。
3. **终结幂等**。跑完又被 cancel 时，「成功」不能被改写成「取消」，否则补播时状态与事件对不上。
4. **暂停点必须在波次末**。同波次可能还有别的工具在并行跑，提前挂起会让那些结果随收敛丢失。
5. **路径穿越**。turn_id 来自前端，直接拼进文件名就是 `../../config.json`。

### 这次做到哪一步

- **选事件溯源**（与仓库既有 trace 架构同源）：turn 只存**游标**，事件仍在 trace 里——一份真相，回滚语义天然一致。
- **第 2 条**：seq 是 **trace 绝对下标**，补播直接把 `after_seq` 交给既有的 `trace.read(after=N)`，中间零换算。
- **第 3 条**：`mark_terminal` 只从非终结态迁移，且**保持第一次结论**（测试 `terminal_transition_is_idempotent` 锁这条）。
- **第 4 条**：`paused_by_ask` 在波次内只记录、波次末统一收敛（`G29` 的注释写明了理由）。
- **第 5 条**：`valid_turn_id` 白名单（字母数字开头 + 字母数字/`-`/`_` + ≤64），测试锁 `../config` 与 `a/b` 被拒。
- **暂停**：`ask_user` 保留工具，命中即写 `paused` + 问题 + `tool_call_id`，**不进下一轮 LLM**（那会花一次钱再让模型自己说「我在等回答」）。回复时 `apply_reply` 把答案按 `tool_call_id` 接回，并把「问题 + 回答」**同时**写 memory 与本轮 `messages`——只写 memory 的话本轮模型根本看不到（这是端到端用例抓到的真 bug）。
- **保留策略**：24 条/会话，只淘汰终结态（删 running/paused 等于让前端失去补播目标）。
- **没做**（诚实边界）：host 侧没有 `/api/turns` 路由。补播目前经 `agent-loop` 的 `turn/replay` / `turn/list` op 可达，前端要接时再加薄路由即可；`ask_user` 断线重连后前端尚未渲染提问卡。

## 四、一句话总结这次的位置

三步都是**把已被验证的机制搬到自己的形态上**，不是照抄：

- 工具：抄「按需声明」，不抄「检索式注入」（规模不够，收益无法证明）；
- 记忆：抄「三层分工」，不抄「语义检索」（同上）；
- 回合：抄「事件溯源 + 暂停是一等状态」，不抄「快照恢复」（与既有 trace 架构冲突）。

三处共同的取舍是**先能测量，再谈优化**——每条机制都配了可机跑的判据（`bytes_read == index 大小`、`deferred` 不进清单但调用照通、`turn_id` 与游标区间的端到端断言），而不是「实现了就算」。
