# 工具调用机制诊断与优化报告（实测版）

> 任务 T-20261116-13 · 2026-11-16
> 对标详表：`outputs/agent-loop-对比-codex-pi-dsh-opencode.md`
> 实施计划与验收：`outputs/agent-loop-优化PLAN.md`

## 一、结论先行

**「单日约 2000 次计费调用」不是工具调用太多，而是每轮请求都携带 ~170–200K tokens 的固定上下文。**
当日 2,913 次请求、2,108 credits，其中 **77.1% 的 credits 来自 cache_read**（缓存前缀）——
缓存本身工作正常（命中率 96.7%），问题是**被缓存的东西太大**，且每轮重发。

实测定价（最小二乘拟合，误差 0.1%）：
```
credits ≈ 1.020e-05 × in + 3.260e-06 × cache_read + 1.223e-04 × out + 0.0267
```
→ cache_read 单价 = input 的 **32.0%**，output = input 的 **12.0 倍**。

## 三、四个机制性根因（按贡献排序）

### R1（77.1% 的 credits）每轮携带 ~170–200K tokens 的固定上下文

- 每会话首个请求的 cache_read 中位 = **170,060 tokens**（p75=262,586，max=567,837）。
- 每轮新增历史仅 **~333 tokens/轮**（斜率回归）——**上下文体积几乎全是固定部分**。
- 固定部分的真实构成（已排除误判）：
  - SYSTEM.md 实际仅 **5,010 字符（≈1.7K token）**，不是 10KB（此前按字节数误判）；
  - 工具 schema 合计 **≈700 tokens**；
  - 技能附录（18 个技能全量 description）**≈1,273 tokens**；
  - **压缩保留的 30 条历史 ≈ 120–150K tokens** ← **真正的大头**。
- 机制：`compaction.rs` 的 `memory.summarize` 持久化时留 `COMPACT_KEEP=30` 条，
  这 30 条**每轮原样发给模型**（`perceive` 拉全量 → 进工作集 → 随请求发出）。

### R2（放大器）单 chat 内历史永不压缩 → 成本 O(N²)

- `maybe_compact` 只在 chat **开头**调一次（`chat.rs:464`），轮内不再压缩；
- 压缩的 token 闸用 `ctx_budget()`，而它对云端 provider **恒为 0**
  （`config.rs`：`context_window` 只对 ollama 生效）→ **云端 token 闸整个禁用**；
- 结果：371 轮的单会话累计 cache_read = **47.3M**，末段每轮仍重发全部历史。

### R3（闸门失效）token 预算口径漏 9.4 倍真实消耗

- `budget.rs::UsageAcc::total()` = `input + output`，**完全不计 cache_read**；
- 实测：今日「预算闸口径」19.0M vs 「真实计费当量」179.0M → **漏 9.4 倍**（单会话 7.6×–35.3×）；
- 叠加 `config.json` 的 `token_budget=0` / `budget_secs=0` / `llm_context_tokens=0`——
  **三重刹车全部失效**。

### R4（提示词层）并行度塌陷 + 失败连锁 + bash 冗余

- 工具调用/轮 = 1.47（38 个 chat 几乎每轮 1 个工具）；
- **整条提示词从未告诉模型「一次回复可以发多个 tool_call」**——这是并行度塌陷的直接原因；
- 工具失败 161 次，每次失败至少多烧一轮（典型：找 board.json 连续 20+ 轮盲试）；
- bash 占工具调用 47%，其中 **93% 以 `cd` 开头**（提示词已明令禁止，但长提示词里权重不足）。

## 四、被推翻的假设（留档）

| 假设 | 实测结论 |
|---|---|
| 「prompt cache 没生效」 | 命中率 **96.7%**，缓存工作正常；问题是**被缓存的固定前缀太大** |
| 「历史膨胀是主因」 | 历史增量仅 ~333 tok/轮，与轮数相关性 **−0.05** |
| 「重试/compact 是主因」 | 今日 retries=3、compaction=12，量级可忽略 |
| 「每个工具一次 LLM」 | usage/round = **1.22**，一轮一次请求 |
| 「SYSTEM.md 有 10KB」 | 实际 5,010 字符 ≈ 1.7K token（此前按字节数误判） |
| 「trace 只有 6 个 chat」 | `--latest` 只看了 main.jsonl；全量（含各实例）今日是 20 chat |

## 五、已实施的优化（18 个补丁，全部可回退）

| 编号 | 改动 | 针对 | 预期收益 |
|---|---|---|---|
| P0A-1/2/3 | 预算口径计入 `cache_read × CACHE_CREDIT_WEIGHT`（缺省 0.32，置 0 退回旧口径）+ 3 条单测 | R3 | 预算闸可见度：漏 9.4× → 漏 <1.2× |
| P0B-1/2/3 | 新增 `CTX_BUDGET_TOKENS`（缺省 64K）与 `workset_budget()`（压缩用，与 `ctx_budget` 的硬收紧分离） | R2 | 云端 token 闸从「禁用」变「启用」 |
| P0B-4/5 | 压缩 token 闸改用 `workset_budget()`；`maybe_compact` 拆出 `maybe_compact_with_keep`（轮内保留 8 条 vs 开头 30 条） | R2 | 轮内压缩可用 |
| P0B-6 | **主循环轮末**按 token 闸调用压缩（此前只在 chat 开头判一次） | R2 | 长会话每轮历史 O(N) → O(1) |
| P0C-1/2/3 | 新增 `trim_workset_by_tokens()`：按 token 预算裁工作集尾部（保留 system 头、丢弃前缘孤儿 tool 消息），chat 开头与轮内各调一次 + 3 条单测 | **R1** | 每请求 cache_read 平台值 170–200K → ≤64K |
| P0D-1/2 | bash 执行层静默剥前导 `cd`（helper 放文件末尾，避免与内置 P1 补丁锚点震荡）+ 7 条单测 | R4 | cd 前缀 93% → ~0 |
| P0D-3 | 系统提示词末尾加「同波次多工具调用纪律」（含「结果按提交顺序回喂」消解并行乱序误判） | R4 | 工具调用/轮 1.47 → 目标 ≥2.0 |
| P0D-4/5/6 | read_file / list_dir / edit_file 的 NOT_FOUND 错误带纠偏建议（用 list_dir 确认，别用 bash 盲试） | R4 | 失败连锁轮次 ↓ |

**未实施（实测不支持）**：P2-E「重试收口」——重试发生在 LLM 层且今日仅 3 次，收益可忽略。
