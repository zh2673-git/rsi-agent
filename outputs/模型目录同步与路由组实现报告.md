## 1. 模型目录同步（P1）

### 1.1 设计约束

- `/v1/models`（Magpie 网关，`:3425`）是**模型目录的单一事实源**。RSI 不再自建一份清单去猜。
- 同步请求**不带 `?provider=`**：带 provider 会让网关只返回该 provider 的子集，前端拿到的「目录」就变成了「某个 provider 的目录」，两边口径分裂。
- **不静默换模型**：当前模型不在新目录里时，保留用户的值为「（自定义…）」条目，绝不悄悄改成第一个。
- 失败必须**可见**且**可重试**（不吞异常）。

### 1.2 落地点

| 位置 | 内容 |
|---|---|
| `runtime/crates/host/src/web/static/app-settings.js` | `ensureCustomOption` / `modelCatalogStatus` / `applyModelCatalog` / `autoSyncModels`；`loadConfig` 重写「先备自定义项 → 保留用户手选 → 按已保存配置自动同步」 |
| `runtime/crates/host/src/web/static/index.html` | model 字段下方新增 `#llm-model-sync` 状态行 |
| `scripts/patches/p1-modelsync-a..d.json` + `p1d2..p1d6` | 补丁链（核心区改动一律走补丁，见 §8） |

行为细节：

1. **打开设置即同步**：`loadConfig()` 末尾 `await autoSyncModels()`——状态行立刻显示同步结论，不需要用户点「刷新」。
2. **状态行文案**（实测）：`已按已保存配置同步 96 个模型`。
3. **并发合并**：同一时刻只允许一次在途 `fetchModels()`，保存后 `await loadConfig()` 不再二次带 provider 拉取（历史上这里会打两次请求、互相覆盖）。
4. **失败可见 + 重试**：网络失败/解析失败在状态行红字 + 「重试」按钮，不静默回落到旧列表。

### 1.3 判据脚本

新增 `scripts/verify-model-sync.py`（3473 字节，仅标准库，只读）：

```
python scripts/verify-model-sync.py [--gw 3425] [--rsi 8710]
```

判据四条，全满足才 exit 0：

1. 网关 `/v1/models` 条数 == RSI `/api/models` 条数；
2. 逐 id **相等**（集合相等，不只是数量相等）；
3. RSI 侧无重复 id；
4. RSI 侧至少 1 个 `auto/*`（防止「只剩静态清单、路由组没进目录」这种假同步）。

实测：

## 2. Trae / WorkBuddy 模型差异可解释

差异不是 bug，是**账号权限 + 上游暴露面**的差。逐 provider 实测（`.scratch/_prov_counts.txt`，`magpie provider models <id>` 与 `magpie accounts` 联查）：

| provider | total | 已暴露 | rc | 账号 |
|---|---:|---:|---:|---|
| `trae-cn` | 94 | **30 / 94** | 0 | 用户2735416860 Credits（`Trae CN's sign-in`） |
| `workbuddy` | 16 | **16 / 16** | 0 | zh2673 Free plan |
| `kiro` | 5 | **5 / 5** | 0 | 3090454653@qq.com Kiro Free |
| `kilo` | 13 | **13 / 13** | 0 | — |
| `opencode-zen` | 86 | **24 / 86** | 0 | — |
| `trae-global` / `workbuddy-ai` / `qoder` / `qoder-cn` / `qwenwork` | — | — | **1** | 未登录 |

**trae-cn 只暴露 30 / 94 的原因**：插件实时目录里有 94 个模型，但 RSI 侧只暴露被判为可用/可计费的那个子集（`trae-cn` 的模型清单与 Credits 账户绑定）。这不是同步失败——同步是「网关给什么、RSI 收什么」，网关自己也只给 30 个。

已做过的一次真实暴露操作（前序）：Trae 侧新增 6 个 minimax 模型（`minimax-m3.1-flash`、`minimax-m3.1-flash-max`、`minimax-m3`、`minimax-m3-max`、`minimax-m2.1`、`minimax-m2`），`trae-cn` 从 **24 → 30 of 94**。全程走 CLI（`magpie provider model add`），未直接改 `~/.config/magpie/providers.json`。

**未登录的 5 个 provider**：`magpie provider models <qoder|qoder-cn|qwenwork|trae-global|workbuddy-ai>` 一律返回

```
no provider "X" — magpie providers lists them
```

即「插件装了、但没登录 → 不进目录」。这与前端「登录渠道按已安装插件动态显示」的语义一致：登录之后才可能出现在模型目录里。

### 3.4 `auto/beam-free` 为什么回不来

```
$ magpie group show auto/beam-free
no group "auto-beam-free"
$ magpie group restore auto/beam-free
no group "auto-beam-free"
```

`providers.json` 只有 3 个 provider（`opencode-zen` / `kilo` / `trae-cn`），全文不含 `beam`。**根因**：found-group 由「≥2 个 provider 有同名模型」派生，opencode-zen 侧已经没有 beam-free 模型 → 派生源消失 → 组既不显示也无从 restore。结论：**按 8 组写，不按 9 组写**。

命令勘误：`magpie group list` **不是**合法命令（返回 `no group "list"`），列全部组用 `magpie groups`，查单组用 `magpie group show <id>`。

## 4. `auto/<model>` 可创建并路由

- 创建：面板「新建组」→ 填 public id（`auto/xxx`）+ 选成员 + routing + stays → CLI 落盘。
- 路由：`auto/*` 由 Magpie 侧 `smart` 策略在成员间选路，RSI 只发 `model: "auto/xxx"`。
- 目录可见性：`auto/*` 会出现在 `/v1/models` 与 `/api/models`（实测 8 个），因此能被前端选中。
- 一致性由 §1.3 的判据脚本守护（「至少 1 个 `auto/*`」是硬条件之一——这条就是为了防「建了组但没进目录」）。

## 6. 动态登录 / 签到 / 免费渠道（P3）

### 6.1 从硬编码改为按插件动态渲染

旧实现：前端硬编码按钮 id（`upstream-login-qoder`、`upstream-login-minimax` …），插件换一套登录方式就静默失效，而且 `minimax` 这个 provider 在清单里**根本不存在**，按钮纯属死块。

新实现：

- 后端 `misc.rs` 新增 `checkin_provider` / `plugin_providers` / `method_usable` / `usable_method` / `upstream_providers`，重写 `upstream_login`；
- 新路由 `("GET", "/api/upstream/providers")`（注册在 `POST /api/upstream/start` **之后**，避免前缀吞掉）；
- 前端 `index.html` 把按钮容器换成 `<span id="upstream-login-btns">`（空容器，内容全动态）；
- 前端 `app-settings.js` P3 段：`refreshCheckinProviders(force)` / `loginProvider(pid,label,btn)` / `renderCheckinState` / `refreshCheckinAccounts`；`PN` 映射去掉 `minimax`。

判据（**这是本项唯一正确的判据**）：UI 上的按钮**集合 / 顺序 / `usable` 标记**必须逐一等于 `/api/upstream/providers` 的返回。不是「页面上有没有某个 id」。

> 曾走过一次弯路：最初写「账号区不应有 Qoder 登录按钮」的断言，FAIL。原因是 Qoder 插件（`opencode-qoder-auth`）**确实已安装且确实提供 qoder / qoder-cn / qwenwork / qwenwork-enterprise 的登录**——删掉的是**硬编码的 id**，不是「Qoder 不能登录」。判据改成集合对等后 27/27 通过。

### 6.2 实测

`GET /api/upstream/providers`（隔离实例，随机空闲端口）→ **9 个**：

- 8 个 `usable: true`
- `qwenwork-enterprise` `usable: false`，唯一 method 是「Sign in with QwenWork 企业版（输入企业域名）」（该 method 实际挂死 >90s，实测过，故禁用）
- `workbuddy-ai` / `workbuddy` / `kiro` 的 **API key** method 为 `usable: false` 且带 `placeholder`（缺 key，前端灰显并在 `title` 给终端命令）

浏览器侧：登录按钮 **9 个**，8 可用、1 禁用且 `title` 含 `magpie plugin login qwenwork-enterprise`；`#upstream-checkin` 仍在；状态行「已登录 12 个账号（11 个有积分）」；无 JS 报错。

### 6.3 签到

- **签到真命令是 `magpie accounts checkin`**（WorkBuddy 每日签到），**不是** `magpie checkin`（不存在）。
- `magpie accounts` 是订阅/额度总览。
- 判据不得用「返回里有 `checkin` 键」来推断签到能力——键名是代理指标，换个包名就误判。改为「`usable_method` 判定 method 是否真能调用」（有 `placeholder` 的 method 不给 `stdin`；`qwenwork-enterprise` 不喂 `stdin`）。

### 7.3 `num_ctx_passthrough_follows_context_window` 的真实状态（必须如实记录）

**这不是「全绿」，而是一处 HEAD 既有的测试夹具缺陷，本轮已定位并修复。**

- 现象：修之前 `cargo test -p react-agent-agent-loop --test react_mocks` 为 **47 passed / 1 failed**，panic 在 `tests/react_mocks.rs:1954`，`left: Null  right: Number(4096)`。
- **是否为本轮引入：不是。** 用 `git worktree add .scratch/head-wt HEAD`（`0162db4`，未含本轮任何改动）单独构建该 crate 后跑同一条用例，**同样 RED、同一行、同一断言**。
- **根因**：该用例把 `LLM_CONTEXT_TOKENS` 设成 `4096`，于是发送预算 `4096 × 0.7 = 2867` tokens；但用例**没有**钉死系统提示词，默认链会去读 `WORKSPACE_ROOT/SYSTEM.md`，本仓库的 `SYSTEM.md` 实测约 **3.2K tokens**（5010 字符，其中 2615 个宽字符）。单这一条就吃掉整个预算 → `context::tighten_for_context` 连「窗口减半 → tool_result 限额减半」都救不回来，直接返回 `CONTEXT_OVERFLOW`（**请求不发出**）→ q2 的 `plan()` 从未被调用 → `captured.last()` 还是 q1 的 payload（q1 本来就没 `num_ctx`）→ 断言读到 `Null`。
- 验证该根因：同一条用例，仅额外 `set AGENT_SYSTEM_PROMPT=SYS` 即 **PASS**（`.scratch/_nc2.log`）。这排除了「env 时序 / `LLM_PROVIDER` 不是 ollama」这一备选假设。
- **修复**：新增补丁 `P0E-NUMCTX-FIXTURE-1`（`scripts/patches/p0e1-numctx-fixture.json` + `blocks/p0e1-numctx-anchor.txt` / `blocks/p0e1-numctx-patch.txt`），在 `EnvGuard` 里加 `AGENT_SYSTEM_PROMPT` 并在用例开头 `set_var(..., "SYS")`，与同文件 compaction/tighten/degrade 那组 token 闸用例做法一致。
- 修复后：`react_mocks` **48 passed / 0 failed**，整套 crate **127 passed / 0 failed**。
- **教训（写进代码注释）**：这不是 num_ctx 透传的问题，是「测试夹具隐式依赖了仓库里某个文件的体积」——同一份代码在 `SYSTEM.md` 更短时全绿、变长后变红，且红的断言指向一个与提示词长度毫无关系的字段。这类红最难查，必须在夹具里钉死所有影响预算的输入。
